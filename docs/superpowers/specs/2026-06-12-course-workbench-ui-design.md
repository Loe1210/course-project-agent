# 课设通 Agent 助手前端与流程重构设计文档

## 1. 设计目标

本次设计不是简单更换前端皮肤，而是同时重构以下两部分：

1. 前端界面从“深色三栏工作台”调整为“浅色 Codex 风格对话主界面”。
2. 后端能力从“完整方案”和“产物生成”两条相互分离的流程，升级为“PAR 主流程内自动联动产物生成 Agent”的一体化课设方案生成流程。

最终目标是让“课设通 Agent 助手”看起来像一个更接近 Codex 桌面端的中文课设助手，同时在能力上真正具备：

- 对话问答
- 完整课设方案生成
- 自动产物联动生成
- 课设资料上传增强知识库
- 方案审查与补全建议

## 2. 本次重构的核心判断

### 2.1 前端判断

用户需要的不是传统后台式工作台，而是更像 Codex 桌面端的浅色对话应用。

因此页面主次关系要改为：

- 中间对话区最大化
- 左侧是轻量导航，而不是重型功能台
- 右侧结果面板默认隐藏，只在需要时展开
- 输入框固定在底部，成为最主要的交互入口

### 2.2 流程判断

当前系统里“完整方案”和“产物生成”是分开的，这不符合课设助手的最终体验。

新的目标应该是：

- 用户发起一次完整课设请求
- PAR 主流程负责拆解、规划、整合
- 产物生成能力作为 PAR 内部子阶段自动执行
- 用户最终拿到的不只是“方案描述”，而是一整套可直接使用的课设材料

### 2.3 RAG 判断

RAG 不能只停留在“系统预置知识库”，也不能在前端中消失。

新的界面必须支持用户上传自己的课设资料，经过：

- 文件上传
- 文档分片
- 向量化
- 写入 Milvus
- 检索增强回答

形成真正可用的知识库增强链路。

## 3. 产品定位

“课设通 Agent 助手”定位为：

> 一个面向大学生软件课程设计场景的中文智能助手，采用 Codex 风格对话界面，以 PAR 编排为主流程，融合知识库、自动产物生成和方案审查能力，帮助用户从选题、规划、产物、报告到答辩形成完整闭环。

这意味着产品既不是普通聊天机器人，也不是单纯的后台管理系统。

## 4. 新的界面结构

## 4.1 总体布局

页面采用“左轻右重、中间主导”的布局：

- 左侧：浅色轻导航栏
- 中间：大对话区
- 底部：悬浮输入区
- 右侧：按需展开的辅助面板

与之前版本相比，变化重点是：

- 去掉默认常驻的大右栏
- 去掉深色控制台气质
- 去掉“模式像后台菜单”的压迫感
- 强化聊天流和任务流的一体化体验

## 4.2 左侧导航栏

左侧栏结构参考 Codex 桌面端，但增加课设能力入口。

建议包含：

1. 顶部快捷入口
   - 新对话
   - 搜索

2. 模式区
   - 课设对话
   - PAR 完整方案
   - 方案审查

3. 知识库入口
   - 知识库

4. 历史会话列表
   - 展示最近会话标题
   - 展示最近更新时间

设计说明：

- “产物生成”不再作为左侧主模式单独并列展示
- 产物生成会合并进 PAR 主流程，但仍在界面中保留“单独生成某类产物”的快捷入口
- 左侧重点是会话导航，不是功能堆叠

## 4.3 中间主对话区

中间区域是页面视觉核心，宽度优先保证给对话流。

包含：

1. 顶部轻量标题区
   - 当前会话标题
   - 当前模式标签
   - 当前知识库状态提示

2. 对话消息流
   - 用户消息
   - 助手消息
   - 流式输出消息
   - 结构化结果消息

3. 消息级能力块
   - 当为 PAR 模式时，在消息内展示阶段进度
   - 当命中知识库时，在消息内展示知识来源提示
   - 当自动生成产物时，在消息内显示产物摘要卡片

中间区不再默认拆成多个工具面板，而是采用“消息承载结果”的方式，更贴近 Codex 桌面端体验。

## 4.4 底部输入区

底部输入区采用大尺寸圆角输入框，固定在页面底部，成为整个页面的交互中心。

建议内容：

- 左侧按钮：
  - 上传资料
  - 快捷动作

- 中部：
  - 主输入框

- 输入框上方轻量上下文标签：
  - 当前模式
  - 当前题目
  - 当前技术方向
  - 当前技术栈

- 右侧：
  - 发送按钮
  - 流式生成按钮

输入区目标是尽量接近用户给出的 Codex 参考图风格。

## 4.5 右侧辅助面板

右侧面板默认不显示。

仅在以下场景展开：

1. PAR 模式已生成结构化产物时
2. 方案审查模式输出了缺失项和建议摘要时
3. 用户主动打开知识库管理面板时

右栏内容按场景变化：

### PAR 结果场景

- 产物目录
- 数据库设计
- 接口设计
- 项目结构
- 报告大纲
- 测试用例
- 答辩问答

### 方案审查场景

- 完整性评分摘要
- 缺失项列表
- 风险点
- 修改建议

### 知识库场景

- 已上传文档列表
- 入库状态
- 文档来源
- 删除或重新入库入口

设计原则是：

- 右栏是“辅助查看器”
- 不是默认主舞台

## 5. 模式与能力重组

## 5.1 最终主模式

主模式调整为三种：

1. 课设对话
2. PAR 完整方案
3. 方案审查

## 5.2 产物生成的定位调整

“产物生成”不再是与 PAR 完整方案完全平级的独立主流程。

新的定位是：

- 它是 PAR 主流程内部自动触发的一组子能力
- 同时作为快捷工具保留“单独生成某项产物”的能力

也就是说：

- 主路径：一次请求自动生成完整方案和配套产物
- 快捷路径：用户也可以单独补生成数据库、接口、报告等

## 5.3 知识库的定位

知识库不是第四个主模式，而是一个贯穿全系统的增强能力。

它的入口在：

- 左侧“知识库”管理入口
- 输入框左侧“上传资料”按钮

它的作用范围覆盖：

- 课设对话
- PAR 完整方案
- 方案审查
- 单项产物补生成

## 6. PAR 与产物生成合并后的流程设计

## 6.1 当前问题

当前系统中：

- `CourseProjectAgentService` 负责 Supervisor / Planner / Executor
- `ArtifactGenerationService` 负责数据库、接口、项目结构、报告等单项产物

二者彼此独立，未形成统一工作流。

## 6.2 新的目标流程

新的 PAR 流程应升级为：

```text
course_project_supervisor
  ├── planner_agent
  ├── solution_agent
  ├── database_artifact_agent
  ├── api_artifact_agent
  ├── structure_artifact_agent
  ├── report_artifact_agent
  ├── test_artifact_agent
  └── defense_artifact_agent
```

执行顺序建议为：

1. Supervisor 识别课设目标、关键交付物和风险
2. Planner 形成总体规划
3. Solution Agent 生成完整课设方案正文
4. 各类 Artifact Agent 生成配套产物
5. 聚合器整理成统一返回结构

## 6.3 PAR 最终输出结构

PAR 模式最终不应只返回三段文本，而应返回一个聚合结果，至少包含：

- supervisorResult
- plannerResult
- solutionResult
- databaseDesign
- apiDesign
- projectStructure
- reportOutline
- testCases
- defenseQa
- knowledgeReferences
- summary

这样前端才能在：

- 中间聊天流中展示主线结果
- 右侧辅助面板中展示结构化产物切片

## 6.4 前端上的展示方式

前端接到 PAR 聚合结果后：

1. 中间对话区先展示：
   - 方案摘要
   - 分阶段执行结果
   - 最终完整方案正文

2. 若用户展开右侧面板，再查看：
   - 数据库设计
   - 接口设计
   - 项目结构
   - 报告大纲
   - 测试用例
   - 答辩问答

3. 用户还可以单击某个产物做：
   - 复制
   - 单独补生成
   - 继续追问

## 7. RAG 上传与知识库管理设计

## 7.1 用户视角

用户应该可以上传自己的课设资料，例如：

- 老师给的课程设计任务书
- 学长学姐的报告模板
- 评分标准
- 自己整理的需求说明
- 参考接口文档

上传后，系统应明确告诉用户：

- 文件已保存
- 文档已分片
- 是否向量化成功
- 是否写入知识库成功

## 7.2 后端链路要求

上传流程必须显式包含：

1. 文件保存
2. 文档分片
3. 向量化
4. 写入 Milvus
5. 返回状态

当前后端已有基础实现，但需要加强返回结果，不能只在日志中记录失败。

新的接口返回应区分：

- 文件上传成功但入库失败
- 文件上传成功且入库成功
- 入库成功的分片数
- 错误原因

## 7.3 前端交互设计

上传资料有两种入口：

1. 输入框左侧快捷上传
2. 左侧知识库入口中的集中管理上传

知识库面板应展示：

- 文件名
- 上传时间
- 入库状态
- 来源路径
- 失败原因

## 7.4 知识引用展示

在对话或 PAR 返回中，若命中了知识库，应提供轻量来源提示，例如：

- 已参考知识库资料
- 参考文档名称列表

不要求在第一版做到复杂引用弹窗，但至少要让用户知道回答是否基于其上传资料生成。

## 8. 技术实现方向

本阶段仍保持前端技术栈不变，继续采用：

- `src/main/resources/static/index.html`
- `src/main/resources/static/app.css`
- `src/main/resources/static/app.js`

原因：

- 与当前 Spring Boot 项目结构保持一致
- 改造成本低
- 能快速演示
- 便于先完成交互重构，再决定是否引入前端框架

## 9. 状态管理要求

前端至少需要管理以下状态：

- 当前模式
- 当前会话 ID
- 当前会话列表
- 当前题目
- 当前技术方向
- 当前技术栈
- 当前上传文件状态
- 当前知识库状态
- 当前右侧面板是否展开
- 当前 PAR 聚合结果
- 当前流式输出内容

## 10. 错误处理要求

所有错误文案必须为中文，并尽量贴近用户操作位置。

至少处理以下错误：

- 课设题目为空
- 请求体为空
- DashScope 未配置
- Milvus 未启动
- 向量化失败
- 文档上传成功但入库失败
- 流式输出中断
- PAR 主流程某个子产物生成失败

对于 PAR 子产物失败，策略建议是：

- 主流程不整体崩溃
- 返回“主方案已生成，但部分产物生成失败”
- 在右栏中明确标出失败项

## 11. 验收标准

本设计实现完成后，应满足以下验收目标：

1. 页面整体气质接近用户给出的 Codex 桌面端截图
2. 页面为浅色主基调，中间对话区占主要空间
3. 左侧保留新对话、搜索、模式入口、历史会话和知识库入口
4. 右侧面板默认隐藏，只在需要时展开
5. 用户可上传课设资料并触发真实 RAG 入库流程
6. PAR 模式能同时输出完整方案和多类配套产物
7. 对话、方案、审查、知识库相关提示全部为中文

## 12. 本阶段范围边界

本轮重构不包含以下内容：

- 引入 Vue 或其他新前端框架
- 登录与账号体系
- 数据库存储真实历史会话
- 富文本编辑器
- 多文件夹级知识库权限管理

本轮重点是：

- 让界面像 Codex
- 让 RAG 真正可见
- 让 PAR 与产物流程真正合并

## 13. 后续实现顺序建议

建议后续实现顺序为：

1. 重构前端布局与浅色视觉
2. 重构前端模式与消息流交互
3. 增加知识库上传与状态显示
4. 重构 PAR 返回结构
5. 将 ArtifactGenerationService 能力并入 PAR 主流程
6. 调整右侧辅助面板为按需展开
7. 做联调与验收
