# 课设通Agent助手项目拷打

这份文档用于面试前复习和模拟追问，重点不是背概念，而是把“课设通 Agent 助手”讲成一个有真实场景、有技术拆解、有工程落地、有后续优化空间的 AI Agent 项目。

## 项目概览

### 课设通Agent助手

课设通 Agent 助手是一个面向大学生软件课程设计场景的 AI Agent 系统。它不是普通聊天机器人，而是把软件课设过程中常见的选题、需求分析、数据库设计、接口设计、项目结构、报告大纲、测试用例和答辩准备整合成一套可执行流程。

系统核心由四部分组成：

1. RAG 知识库：支持上传课程设计任务书、评分标准、报告模板、优秀案例等资料，通过文档分片、Embedding 向量化和 Milvus 检索，为回答和方案生成提供依据。
2. 对话 Agent：基于 ReAct 思路处理自由问答、多轮上下文和即时工具调用，适合解释概念、推荐选题、局部修改方案等交互场景。
3. 课设任务 Agent：基于 PAR/Plan-Execute-Replan 思路，将完整课设任务拆成 Supervisor、Planner、Executor 等阶段，负责规划并聚合完整课设方案。
4. 工具与前端工作台：封装选题推荐、数据库设计、接口设计、项目结构、报告大纲、测试用例、答辩问答等工具，并提供类似 Codex 的浅色对话工作台。

### 项目介绍：

**30 秒版本：**

我做的是一个面向大学生软件课设场景的 AI Agent 助手。它解决的是学生在课程设计里不会选题、不会拆需求、不会设计数据库接口、报告和答辩材料准备成本高的问题。系统基于 Spring Boot 和 Spring AI Alibaba，实现了 RAG 知识库、ReAct 对话 Agent、PAR 任务 Agent、工具调用和 SSE 流式输出。用户可以上传老师给的任务书和评分标准，系统会结合知识库和工具生成完整课设方案以及数据库、接口、报告、测试、答辩等配套产物。

**1 分钟版本：**

课设通 Agent 助手的背景是软件课设任务并不是一个简单问答，学生通常需要完成选题、需求分析、系统设计、数据库设计、接口设计、测试和答辩准备。普通大模型虽然能生成一段方案，但容易泛化，也不能保证符合课程评分标准。

所以我把系统拆成三层能力。第一层是 RAG 知识库，用户可以上传任务书、评分标准、报告模板和案例资料，后端会做分片、Embedding 和 Milvus 入库。第二层是 ReAct 对话 Agent，负责自由问答、多轮上下文和即时工具调用。第三层是 PAR 课设任务 Agent，通过 Supervisor、Planner、Executor 完成复杂任务拆解，并联动数据库、接口、报告、测试、答辩等工具生成完整课设产物。

**3 分钟版本：**

这个项目的核心不是调用大模型接口，而是把课设这个复杂任务工程化。用户输入一个题目，比如“校园二手交易平台”，系统不会直接给一段泛泛的回答，而是先结合用户上传的课程资料做知识检索，再由任务 Agent 判断目标、规划步骤，最后调用不同工具生成需求分析、技术架构、数据库表、接口列表、项目目录、测试用例、报告大纲和答辩问答。

架构上我设计了双主 Agent。对话 Agent 使用 ReAct 思路，适合用户边问边改，比如“这个数据库表合理吗”“帮我补一个接口”“这个技术栈怎么介绍”。任务 Agent 使用 PAR 思路，适合完整方案生成，因为完整课设需要先规划再执行，并且要把多个子产物聚合成一套一致的交付结果。

RAG 部分用于解决模型知识来源不可靠的问题。用户上传的评分标准、报告模板、任务书会经过文档分片、DashScope Embedding 向量化，再写入 Milvus。后续回答时，Agent 可以通过知识库工具召回相关内容，避免只依赖通用大模型知识。

工程上，后端使用 Spring Boot、Spring AI Alibaba、DashScope、Milvus 和 SSE，前端是一个 Codex 风格的浅色对话工作台。项目目前重点验证了课设资料上传、知识库检索、对话问答、任务编排和产物生成的闭环。

### 面试亮点打造

**亮点一：不是普通问答，而是课设全流程 Agent。**

普通大模型只能回答“帮我写一个方案”，但课设通会把课设拆成选题、需求、数据库、接口、测试、报告和答辩多个步骤。面试时要强调：系统输出的不是一段文本，而是一套结构化课设交付物。

**亮点二：RAG 让答案和课程资料绑定。**

没有 RAG 时，模型只能凭通用知识回答；有 RAG 后，可以把老师的评分标准、任务书、报告模板和优秀案例接入生成过程，让答案更贴合课程要求。

**亮点三：ReAct 和 PAR 分场景使用。**

自由问答用 ReAct，因为用户问题不固定，需要动态选择工具；完整课设方案用 PAR，因为它是多步骤复杂任务，需要规划、执行、整合和审查。

**亮点四：工具调用让 Agent 从“会说”变成“能做”。**

数据库设计、接口设计、报告大纲、测试用例这些内容不是全部靠 prompt 临时生成，而是封装成工具，由 Agent 按需调用，提高结构稳定性。

**亮点五：SSE 解决长文本等待体验。**

完整方案输出很长，如果等全部生成完再返回，体验很差。SSE 可以让前端持续接收内容，用户能看到生成过程。

### 成果量化与安全口径

可以稳妥写的量化：

- RAG 分片默认参数：`maxSize=800`、`overlap=100`。
- 检索默认参数：`TopK=3`。
- 支持 `.txt`、`.md` 文档上传进入知识库链路。
- 当前已覆盖上传、产物生成、方案审查、对话和任务编排等核心接口测试。

建议补测后再写的量化：

- 使用 20 份课设资料样例构造问答集，统计 Recall@K 或人工相关性评分。
- 统计完整方案生成耗时、首 token 时间、工具调用成功率。
- 统计产物覆盖度，例如是否生成需求、数据库、接口、测试、报告、答辩六类内容。

面试中更稳的说法：

> 我目前没有直接把“准确率 85%+”写死成线上指标，而是先从工程链路和参数选择上保证可用性。后续我会用标准问答集评估 Recall@K、答案相关性和产物完整性，这样比主观说准确率更可信。

### 面试节奏

推荐顺序：

1. 先讲背景：学生做软件课设的真实痛点。
2. 再讲架构：RAG、对话 Agent、任务 Agent、工具集、前端工作台。
3. 重点讲三个技术点：RAG 链路、ReAct/PAR 区分、工具调用。
4. 主动讲一个难点：复杂任务拆解、RAG 参数选择、长文本流式输出任选一个。
5. 最后讲不足和改进：RAG 评测、引用来源展示、多 Agent 重试与降级。

不要这样讲：

- 不要只说“调用大模型生成课设内容”。
- 不要把 MCP 说成所有能力都已经完全基于 MCP。
- 不要把还没做压测的数据讲成线上真实指标。
- 不要把 Eino、腾讯云日志等 OnCall 项目里的内容硬套到课设通。

## 项目相关问题：

### Part1:Agent架构问题

#### 1. 简单介绍一下你设计的几个 Agent

课设通里主要是双主 Agent 架构。

第一个是对话 Agent，偏 ReAct 模式，负责自由问答、多轮上下文、知识库检索和即时工具调用。比如用户问“这个选题怎么拆需求”“帮我补一个接口”“这个数据库设计合理吗”，这些都适合对话 Agent。

第二个是课设任务 Agent，偏 PAR/Plan-Execute-Replan 模式，负责完整课设方案生成。它内部可以拆成 Supervisor、Planner、Executor。Supervisor 判断用户目标和输入是否完整，Planner 拆解生成步骤，Executor 结合 RAG 和工具输出完整方案及产物。

#### 2. 为什么要设计双 Agent，而不是一个 Agent 全部做完？

因为课设场景里有两类任务：一类是自由问答，另一类是完整课设方案生成。自由问答的问题不固定，需要动态判断是否查知识库、是否调用工具，所以适合 ReAct。完整课设方案是多步骤流程，需要先规划再执行，并保证多个子产物一致，所以适合 PAR。

如果用一个 Agent 做全部事情，prompt 会变得很臃肿，而且简单问题也要走复杂流程，复杂问题又容易直接生成一段混乱文本。拆成双 Agent 后，职责更清晰，也更容易维护。

#### 3. Agent 是什么意思？

Agent 可以理解为具备目标理解、任务规划、工具调用和结果反馈能力的大模型应用。普通大模型只是根据 prompt 生成答案，而 Agent 可以根据目标决定下一步做什么，比如是否检索知识库、是否调用数据库设计工具、是否继续生成报告大纲。

在课设通里，Agent 的价值是把“聊天回答”升级成“围绕课设目标完成任务”。

#### 4. ReAct 是什么？课设通怎么用？

ReAct 是 Reasoning + Acting，也就是让模型在推理和行动之间循环。模型先分析用户问题，再决定是否调用工具，拿到工具结果后继续推理并生成答案。

课设通的对话 Agent 使用 ReAct 思路。比如用户问“帮我设计校园二手交易平台的数据库”，Agent 可以判断这是数据库设计任务，调用数据库设计工具；如果用户问“按照我的评分标准看看方案缺什么”，Agent 可以先调用知识库检索评分标准，再给出审查建议。

#### 5. PAR 或 Plan-Execute-Replan 是什么？

PAR 可以理解为规划、执行、再规划的任务模式。它适合复杂任务，不是让大模型一次性输出所有内容，而是先拆解任务，再分步骤执行，必要时根据执行结果重新调整计划。

课设通的完整方案生成就适合这个模式。比如生成一个软件课设方案，需要完成需求分析、技术选型、系统架构、数据库设计、接口设计、测试用例、报告大纲和答辩问答。PAR 可以让这些步骤有顺序、有结构，也方便后续做状态跟踪和失败重试。

#### 6. ReAct 和 PAR 有什么区别？

ReAct 更适合交互式、不确定的问题。它强调“边想边调用工具”，用户问什么，Agent 就根据当前问题决定下一步。

PAR 更适合目标明确、流程较长的复杂任务。它强调“先规划再执行”，比如完整课设方案生成。

简单说：对话问答用 ReAct，完整课设交付用 PAR。

#### 7. 课设任务 Agent 的 Supervisor、Planner、Executor 分别做什么？

Supervisor 负责识别用户目标、检查输入是否完整、判断是否需要知识库和工具。比如用户只说“帮我做课设”，Supervisor 要提示补充题目、技术方向和产物要求。

Planner 负责拆解任务，把完整课设拆成需求分析、架构设计、数据库、接口、报告、测试、答辩等步骤。

Executor 负责执行计划，调用 RAG 和课设工具，生成最终方案和配套产物。

#### 8. Multi-Agent 是怎么协作的？

课设通的 Multi-Agent 不是多个 Agent 随机对话，而是有明确职责边界。任务 Agent 作为总控，先规划任务，再把数据库、接口、报告、测试、答辩等子任务交给对应工具或子能力生成，最后统一聚合结果。

这种协作方式比“所有 Agent 一起聊天”更可控，因为每一步的输入输出都能被约束，也方便后续增加失败重试和质量审查。

#### 9. 为什么不用一个超长 Prompt 完成全部功能？

超长 Prompt 短期能跑，但维护性差。随着功能增多，prompt 会混杂角色设定、工具说明、流程约束、输出格式和错误处理，很容易互相干扰。

课设通把能力拆成 Agent、工具和服务层：Agent 决策，工具执行稳定任务，RAG 提供外部知识，服务层负责工程编排。这样比把所有逻辑塞进 prompt 更清晰。

#### 10. 你的对话 Agent Prompt 怎么写？

对话 Agent 的 Prompt 重点是中文课设场景、工具使用规则和回答边界。

核心要求包括：

1. 始终使用中文回答。
2. 先理解用户课设目标，再决定是否调用工具。
3. 涉及课程资料、评分标准和报告模板时优先检索知识库。
4. 不确定的内容要明确说明假设，不能伪造来源。
5. 回答要面向课设落地，尽量给出结构化建议。

#### 11. 你的任务 Agent Prompt 怎么写？

任务 Agent 的 Prompt 更强调流程和产物完整性。

核心要求包括：

1. 将用户输入拆解为课设目标、技术方向、产物要求和约束条件。
2. 先规划，再执行，不要直接输出散乱内容。
3. 必须覆盖需求分析、功能模块、技术架构、数据库设计、接口设计、测试、报告和答辩。
4. 需要结合 RAG 召回内容和工具输出。
5. 如果输入不足，要列出缺失信息并给出默认假设。

#### 12. 如何处理多轮对话和上下文记忆？

课设通通过 conversationId 维护会话上下文。短对话可以保留最近几轮原文，长对话需要做摘要压缩，避免上下文无限增长。

理想结构是：system prompt 放最前面，接着放历史摘要，再放最近几轮用户和助手消息，最后放当前问题和工具结果。这样既保证角色和规则稳定，又能让模型理解当前上下文。

#### 13. 对话 Agent 如何处理超出上下文窗口的长对话？

不能把所有历史对话都塞进 prompt。我的方案是保留最近 N 轮关键对话，把更早的内容压缩成摘要，例如当前课题、技术栈、已生成产物、用户偏好和待办事项。

这样可以减少 token，同时保留任务连续性。后续还可以把重要结论写入长期记忆或项目状态表。

#### 14. 你的 system prompt、历史摘要、最近对话顺序怎么排？

推荐顺序是：

1. system prompt：定义身份、规则、语言和安全边界。
2. 历史摘要：压缩后的长期上下文。
3. 最近几轮对话：保留局部语义和用户当前意图。
4. RAG 召回内容和工具结果：提供事实依据。
5. 当前用户问题：让模型聚焦本轮任务。

顺序会影响模型注意力。system prompt 太靠后可能约束变弱；当前问题太靠前又可能导致模型忽略工具结果。

#### 15. 你怎么实现用户意图识别？

目前主要通过 Agent 的语义理解和工具描述来判断意图。比如用户问“推荐题目”时会匹配选题推荐工具；问“数据库表怎么建”时会匹配数据库设计工具；问“按照评分标准检查”时会优先调用知识库。

后续可以增加显式意图分类层，把意图分成咨询问答、知识库检索、完整方案生成、产物生成、方案审查等类型，提高路由稳定性。

#### 16. 如何避免大模型产生幻觉？

我从三层降低幻觉。

第一是输入层，通过 RAG 检索课程资料、评分标准和模板，减少模型凭空发挥。第二是过程层，把数据库设计、接口设计、报告大纲等任务封装为工具，减少自由生成的不稳定性。第三是输出层，要求模型明确假设，不确定内容不编造来源，后续还可以展示引用来源和加入审查 Agent。

#### 17. 如果 Agent 召回答案不准确，大模型会胡说八道吗？

有这个风险，所以不能只依赖大模型自觉。课设通会在 prompt 中要求模型区分“资料依据”和“合理假设”。如果 RAG 没有召回到相关内容，就要明确说明“知识库未检索到直接依据”，然后只能给通用建议。

后续还可以通过相似度阈值、引用来源展示和答案审查来进一步降低风险。

#### 18. 通过 SSE 实现流式输出，为什么不用 WebSocket？

课设通的主要场景是服务端把大模型生成内容持续推给前端，属于单向流式输出。SSE 原生支持浏览器接收服务端事件，实现简单，和 HTTP 生态兼容好。

WebSocket 更适合双向实时通信，比如在线协作、聊天室、游戏等。课设通当前不需要强双向实时通信，所以 SSE 更轻量。

#### 19. SSE 核心怎么实现？

后端可以使用 Spring 的 SseEmitter 创建连接，在模型生成过程中不断向前端发送文本片段、阶段状态或结束事件。前端通过 EventSource 或 fetch stream 接收并拼接内容。

关键点是处理超时、异常和结束事件。生成失败时要发送中文错误提示，不能让前端一直等待。

#### 20. 为什么选择 Spring AI Alibaba，不用 LangChain？

课设通是 Java/Spring Boot 项目。Spring AI Alibaba 能直接对接 DashScope，并且能把工具类、服务类、配置类都纳入 Spring 容器，和后端工程融合更好。

LangChain 很适合 Python AI 应用，但在 Java 项目里使用会增加跨语言部署和调用成本。这个项目更看重 Java 工程落地，所以选择 Spring AI Alibaba。

#### 21. 简单说说 Spring AI Alibaba 是什么框架

Spring AI Alibaba 是 Spring AI 在阿里云通义千问、DashScope 等模型生态上的扩展能力。它可以把大模型调用、ChatClient、Embedding、工具调用等能力接入 Spring Boot 项目，并复用 Spring 的依赖注入、配置管理、测试体系和 Web 框架。

#### 22. 简单说说 Eino 是什么框架

Eino 是字节跳动开源的 Go 语言 AI 应用开发框架，主要用于构建大模型应用、Agent、RAG、工具调用和工作流编排。

但课设通没有使用 Eino。面试里如果被问到，可以说了解它的定位，但本项目为了贴合 Java/Spring 技术栈，选择的是 Spring AI Alibaba。

#### 23. 为什么选择 Eino，不用 LangChain？

这个问题不完全适用于课设通，因为课设通没有使用 Eino。可以这样转回来：

> 我这个项目没有选 Eino，也没有选 LangChain，而是选了 Spring AI Alibaba。原因是项目主技术栈是 Java + Spring Boot，Spring AI Alibaba 能直接复用 Spring 的 Bean 管理、配置、Controller 和测试体系；而 LangChain 更偏 Python 生态，Eino 更偏 Go 生态。

### Part2:RAG知识库问题

#### 1. RAG 是什么？课设通怎么用？

RAG 是 Retrieval-Augmented Generation，也就是检索增强生成。它的核心思想是模型回答前先从外部知识库检索相关资料，再把这些资料作为上下文交给大模型生成答案。

课设通里的 RAG 流程是：用户上传课设资料，后端保存文件，然后由文档分片服务切分内容，再调用 DashScope Embedding 生成向量，写入 Milvus。查询时，把用户问题也转成向量，在 Milvus 中做相似度检索，召回 TopK 相关片段，最后交给 Agent 生成答案。

#### 2. 知识库的使用场景是什么？

主要有四类：

1. 上传老师给的课程设计任务书，帮助 Agent 理解任务要求。
2. 上传评分标准，让方案生成和审查更贴合评分项。
3. 上传报告模板，让报告大纲和章节结构更符合格式要求。
4. 上传优秀案例或历史资料，让选题和方案更接近课程风格。

#### 3. 为什么需要 RAG，直接让大模型回答不行吗？

不够稳定。大模型没有用户课程的具体资料，不知道老师评分标准、报告模板和任务书细节，容易生成泛化内容。

RAG 的价值是把外部资料接进生成过程，让回答有依据。尤其是课设这种强依赖课程要求的场景，RAG 比单纯 prompt 更可靠。

#### 4. 文档上传后需要向量化吗？

需要。如果只是保存文件，Agent 后续很难根据问题快速找到相关内容。向量化的作用是把文本片段转成语义向量，后续用户提问时也转成向量，再通过相似度检索找到相关片段。

课设通的上传链路应该包括：上传文件、保存文件、读取文本、文档分片、Embedding、写入 Milvus、返回入库结果。

#### 5. 文档分块大小和 overlap 怎么选？

课设通默认使用 `maxSize=800`、`overlap=100`。这个参数是折中选择。

分块太小，单个片段语义不完整，容易召回碎片；分块太大，会引入无关内容，并占用更多上下文。overlap 的作用是避免关键信息刚好被切断，比如评分项标题和说明分到两个块里。

面试中可以说：目前先采用经验参数，后续会用标准问答集评估不同 chunk size、overlap 和 TopK 的效果。

#### 6. 检索 TopK 参数怎么选？

TopK 太小可能漏召回，TopK 太大又会带来噪声和 token 开销。课设通默认 TopK=3，是为了在召回覆盖和上下文长度之间做平衡。

后续可以根据不同任务动态调整。例如概念问答 TopK=2 就够，完整方案生成可以 TopK=5，并配合 rerank 或引用筛选。

#### 7. Embedding 是什么意思？

Embedding 是把文本转换成向量表示的过程。语义相近的文本，在向量空间中的距离也更近。

在课设通里，课程资料和用户问题都会被转成向量，然后通过向量相似度检索找到相关资料片段。

#### 8. 召回的相似度算法是什么？

常见相似度算法包括余弦相似度、内积和欧氏距离。RAG 场景通常会使用余弦相似度或内积来衡量两个向量的语义接近程度。

如果面试追问，可以说：具体使用哪种相似度取决于 Milvus collection 的索引配置和 metricType。项目里要保证 embedding 模型、向量维度和 Milvus schema 配置一致。

#### 9. 为什么使用 Milvus？

Milvus 是专门面向向量存储和相似度检索的数据库，适合 RAG 场景。课设资料被 Embedding 成向量后，需要根据用户问题快速召回相似内容，这正是 Milvus 的使用场景。

相比把向量硬存在 MySQL，Milvus 在向量索引、相似度检索和后续扩展上更专业。即使当前数据量不大，使用 Milvus 也能让项目架构更接近真实 RAG 应用。

#### 10. 为什么不直接把所有文档塞进 Prompt？

因为文档多了会超过上下文窗口，而且无关内容会干扰模型。RAG 的价值就是先筛选，只把最相关的片段放进上下文。

这样既节省 token，也能降低噪声，让模型更关注和当前问题相关的资料。

#### 11. 召回和重排有什么区别？

召回是从大量文档片段里快速找出可能相关的一批候选内容，追求速度和覆盖。

重排是对召回结果进一步精排，判断哪些片段更适合当前问题，追求准确性。

课设通目前可以先做向量召回，后续如果要提升准确率，可以加入 rerank 模型或规则重排。

#### 12. 混合 RAG 有什么好处？

混合 RAG 通常指结合向量检索、关键词检索、结构化过滤和重排等多种方法。

它的好处是弥补单一向量检索的不足。比如“第 3 条评分标准”这种问题，关键词检索可能比纯向量更准；而“这个要求是什么意思”这种语义问题，向量检索更合适。

#### 13. 你知道 Agentic RAG 吗？

Agentic RAG 是让 Agent 主动决策如何检索，而不是固定执行“问题 -> 检索 -> 生成”。

普通 RAG 每次都走同样流程；Agentic RAG 可以让 Agent 判断是否需要检索、检索什么关键词、是否多次检索、是否结合工具。课设通的知识库工具已经有 Agentic RAG 的雏形，因为对话 Agent 可以按需调用知识库，而不是每次固定检索。

#### 14. RAG 如何处理文档更新？增量索引怎么做？

文档更新时不能只覆盖原文件，还要处理旧向量。比较稳的做法是给每个文档和每个 chunk 分配 documentId、chunkId、version。

更新时先标记旧版本 chunk 失效，再对新文档重新分片和向量化，写入新版本索引。查询时只检索有效版本。这样可以避免旧内容和新内容同时被召回。

#### 15. 如何评估 RAG 效果？

可以从三个维度评估：

1. 召回效果：Recall@K、命中文档片段数量、人工相关性评分。
2. 生成效果：答案是否引用到正确资料，是否符合评分标准。
3. 业务效果：生成方案是否完整，是否覆盖老师要求的章节和产物。

面试中不要只说“准确率 85%+”，更建议说会构造标准问答集来评估。

#### 16. 如果 RAG 没有检索到内容怎么办？

要明确告诉用户知识库没有找到直接依据，然后给出通用建议或引导用户上传相关资料。

不能让模型假装查到了资料。后续还可以设置相似度阈值，低于阈值时不把片段当作有效依据。

#### 17. 如何避免 RAG 召回无关内容污染答案？

可以从四点处理：

1. 设置相似度阈值。
2. 控制 TopK，避免塞入过多无关片段。
3. 加入 rerank 或关键词过滤。
4. 在 prompt 中要求模型只基于相关片段回答，不相关内容不要强行使用。

#### 18. 知识库入口为什么重要？

因为 RAG 如果只有后端链路、没有前端上传入口，用户就无法把自己的课程资料接入系统。课设通的定位是“结合用户课设资料生成方案”，所以前端必须有资料上传和知识库状态展示。

这也是之前设计中需要补齐的一点：RAG 不能只是后端能力，必须体现在用户工作流里。

### Part3:Tool、MCP问题

#### 1. 你的工具集有哪些 Tool，分别有什么功能？

课设通工具集主要包括：

1. 选题推荐工具：根据技术方向、难度、课程要求推荐课设题目。
2. 数据库设计工具：生成核心表、字段、关系和设计说明。
3. 接口设计工具：生成 REST API 路径、请求参数、响应结构。
4. 项目结构工具：生成前后端目录结构和模块划分。
5. 报告工具：生成课程设计报告大纲和章节要点。
6. 测试用例工具：生成核心功能测试用例。
7. 答辩工具：生成常见答辩问题和回答思路。
8. 知识库工具：调用 RAG 检索课设资料。

#### 2. 为什么需要工具，不让大模型直接生成不行吗？

大模型直接生成可以做 demo，但稳定性不够。工具可以把高频、结构化、可复用的任务固定下来，比如数据库设计必须包含表名、字段、类型、主键、关系；接口设计必须包含路径、方法、参数、返回值。

工具让 Agent 从“会说”变成“能做”，也让输出更容易测试。

#### 3. Agent 是怎么实现工具调用的？

在 Spring AI Alibaba 体系下，可以把工具类注册为 Spring Bean，并用工具注解描述方法用途、参数和返回值。Agent 请求模型时，把可用工具信息传给 ChatClient。

模型根据用户问题选择是否调用工具。如果需要调用，框架会执行对应方法，把结果返回给模型，模型再综合工具结果生成最终回答。

#### 4. Function Calling 的实现流程是什么？

流程可以概括为五步：

1. 后端注册工具方法，并声明工具名称、描述和参数。
2. 用户提问后，后端把消息和工具列表发送给模型。
3. 模型判断是否需要调用工具，并生成工具调用请求。
4. 后端执行工具方法，得到结构化结果。
5. 模型基于工具结果生成最终中文回答。

#### 5. 如何保证模型不会调用错误工具或传递错误参数？

第一，工具描述要清晰，避免多个工具职责重叠。第二，参数要做校验，缺少必要参数时返回中文错误提示。第三，工具执行结果要结构化，避免模型误解。第四，可以在 Agent 层加白名单和路由规则，限制某些场景可调用的工具。

#### 6. 如果工具调用失败怎么办？

工具失败不能让整个对话无响应。应该记录失败原因，返回中文错误信息，并给出可降级结果。

比如数据库设计工具失败时，可以提示“数据库设计工具暂时不可用，我先根据题目给出通用表结构建议”。PAR 流程里还可以记录 failedArtifacts，让用户知道哪些产物生成失败。

#### 7. 工具结果和大模型生成内容怎么整合？

工具负责提供结构化结果，大模型负责解释、补充和组织语言。

比如数据库工具返回表结构，模型再补充设计理由、表之间关系、为什么这样设计。这样既保留工具的稳定性，又保留模型的表达能力。

#### 8. 简历上写了 MCP，谈谈你对 MCP 的理解

MCP 是 Model Context Protocol，可以理解为让 Agent 标准化连接外部工具、上下文和服务的一种协议。它的价值是把工具能力和模型解耦，让不同工具可以通过统一协议被 Agent 调用。

课设通目前核心工具主要是本地 Spring Bean 工具，MCP 更适合作为后续扩展方向，比如接入文档解析器、代码生成器、在线资料检索、课程平台资料读取等。面试时不要夸大成“所有能力都基于 MCP”，更稳的说法是“系统保留了 MCP 扩展思路”。

#### 9. MCP 和普通 Function Calling 有什么区别？

Function Calling 更像是模型调用当前应用内注册的函数，通常和某个模型 SDK 或框架绑定。

MCP 更像标准化协议，把工具、资源和上下文以统一方式暴露出来。它的目标是让不同 Agent 客户端可以连接不同工具服务，减少工具接入的重复工作。

简单说：Function Calling 是具体调用机制，MCP 更偏工具生态和协议标准。

#### 10. 课设通后续哪些能力适合用 MCP 扩展？

适合扩展的能力包括：

1. 文档解析服务：解析 PDF、DOCX、PPT。
2. 代码生成服务：生成后端 Controller、Entity、Mapper、前端页面模板。
3. Git 工具：生成项目后自动提交或导出。
4. 在线资料检索：查询技术文档或课程资料。
5. 本地 IDE 工具：读取项目结构，辅助修改代码。

#### 11. 你知道 Agent Skills 吗？

Agent Skills 可以理解为把某类专业能力封装成可复用技能，比如“生成报告”“设计数据库”“代码审查”“文档解析”。它比单个工具更高一层，通常包含步骤、约束和多个工具组合。

课设通后续可以把“完整课设生成”“报告润色”“答辩模拟”“项目代码生成”做成 Skills，让 Agent 复用更稳定的工作流。

#### 12. 有了 Skill 后项目哪里可以改进？

可以把现在分散的工具组合成更高层的技能。例如“生成完整课设交付物”Skill 内部包含检索资料、生成需求、数据库、接口、测试、报告和答辩，并在最后做完整性审查。

这样用户只需要表达目标，Agent 就能调用一套稳定流程，而不是每次临时判断多个工具怎么组合。

#### 13. 工具调用和 RAG 是什么关系？

RAG 可以作为一种工具提供给 Agent。对话 Agent 不需要每次都固定检索，而是根据问题判断是否调用知识库工具。

比如用户问“你是谁”不需要检索；问“我的评分标准里有没有要求 ER 图”就应该调用 RAG。

#### 14. 工具返回内容如何避免上下文爆炸？

工具不应该返回大量原始文本，而应该返回结构化摘要。RAG 只返回 TopK 片段；数据库工具返回表结构摘要；报告工具返回章节结构。

必要时可以对工具结果再做摘要，避免把过长内容塞进模型上下文。

#### 15. 工具参数如何设计？

工具参数要尽量贴近业务语义，比如 topic、techStack、difficulty、artifactType、requirements，而不是传一大段无法解析的自然语言。

参数越结构化，工具越稳定，也越方便做校验和测试。

### Part4:场景问题

#### 1. 项目背景是什么？为什么会有这个项目？

大学生做软件课设时，常见问题是不会选题，不知道怎么拆需求，不会把数据库、接口、报告和答辩组织成完整方案。普通大模型虽然能回答，但缺少老师任务书、评分标准和报告模板作为依据。

所以我做课设通，把 RAG、Agent 和工具调用结合起来，让课设从零散问答变成结构化流程。

#### 2. 这个项目是用来做什么的？

它用于辅助大学生完成软件课程设计。用户可以上传课程资料，进行课设问答，生成完整课设方案，也可以生成数据库设计、接口设计、项目结构、报告大纲、测试用例和答辩问答。

#### 3. 你在项目里是什么角色？

我是项目负责人，主要负责需求分析、架构设计、后端 Agent/RAG/工具模块实现、前端工作台设计、接口联调和测试验证。

可以强调：这个项目不是只做页面或接口，而是从产品定位、Agent 架构、RAG 链路、工具抽象到前后端联调都参与了。

#### 4. 项目的核心指标是什么？

核心指标可以分三类：

1. 效果指标：RAG 召回相关性、方案完整性、产物覆盖度。
2. 体验指标：首 token 时间、完整方案生成耗时、流式输出稳定性。
3. 工程指标：接口成功率、工具调用成功率、异常降级能力、测试覆盖情况。

#### 5. 项目遇到的最大困难是什么？

最大困难不是调用模型，而是如何让模型稳定完成一个复杂课设任务。课设不是单点问答，它包含知识检索、任务规划、多个产物生成和结果审查。

我的解决方式是把系统拆成 RAG、ReAct、PAR 和工具集。RAG 解决知识来源，ReAct 解决自由问答，PAR 解决复杂任务拆解，工具集解决结构化产物稳定生成。

#### 6. 你觉得做得最好的点是什么？

我觉得做得最好的点是把“课设方案生成”从单次文本生成拆成了可解释流程。用户输入题目后，系统不是直接输出一大段文字，而是通过知识库检索、任务规划、工具调用和产物聚合形成完整交付。

这个设计更接近真实 Agent 应用，而不是简单套壳聊天。

#### 7. 项目有哪些不足？如何改进？

不足主要有三点。

第一，RAG 评测还不够体系化，需要构建标准问答集。第二，多 Agent 编排目前以顺序流程为主，后续可以增加 Replan、重试和降级机制。第三，知识库管理还比较轻量，后续可以支持 PDF、DOCX、引用来源展示和文档删除重建索引。

#### 8. 如果重新设计这个系统，你会怎么改？

我会重点改四点：

1. 增加标准 RAG 评测集，用 Recall@K 和人工相关性评分评估效果。
2. 引入混合检索和 rerank，提高召回准确性。
3. 把 PAR 流程做成更完整的状态机，每个子产物都有状态、重试和降级。
4. 前端增强引用来源展示，让用户知道答案来自哪些文档片段。

#### 9. 项目怎么部署？

可以本地部署或服务器部署。后端是 Spring Boot 服务，前端是 Vite 构建后的静态资源，模型服务对接 DashScope，向量库使用 Milvus。

部署时要配置 DashScope API Key、Milvus 地址、文件上传路径和前后端接口地址。Milvus 可以通过 Docker Compose 启动。

#### 10. 项目用的是什么模型？为什么用这个模型？

项目通过 Spring AI Alibaba 对接 DashScope，聊天生成使用通义千问系列模型，Embedding 使用 DashScope 的 `text-embedding-v4`。

选择它是因为项目技术栈是 Java/Spring Boot，Spring AI Alibaba 对 DashScope 接入比较直接，同时支持 Chat 和 Embedding，能满足对话生成和 RAG 向量化需求。

#### 11. DashScope 是干嘛的？

DashScope 是阿里云灵积模型服务平台，用于调用通义千问等大模型能力。课设通里它主要承担两类能力：一是 Chat Model，用于对话和方案生成；二是 Embedding Model，用于把文档和用户问题向量化。

#### 12. Milvus 有必要配吗？

如果只测试普通对话，Milvus 可以先不配；但如果要测试 RAG 上传、向量化、知识库检索，就必须配置 Milvus。

因为 RAG 的关键不只是上传文件，而是把文档切片向量化后存入向量库，并在提问时召回相关片段。

#### 13. 项目测评怎么做？

目前可以分两层测评。

第一层是工程测试：上传接口是否成功、工具接口是否返回结构化结果、对话接口是否流式输出、PAR 流程是否生成完整产物。

第二层是效果测试：准备一组课程资料和标准问题，检查 RAG 是否召回正确片段，方案是否覆盖评分标准，生成产物是否完整。

#### 14. 如果面试官说项目看起来很简单，你怎么回答？

可以这样回答：

> 如果只看表面，它像是一个 AI 问答系统。但我这个项目的重点不是调用模型接口，而是把课设任务拆成 RAG 知识库、ReAct 对话、PAR 编排、工具调用、SSE 流式输出和结构化产物聚合。真正难的是让模型稳定完成一个完整业务流程，而不是只生成一段文本。

#### 15. 压力面：你们项目的 TPM 是多少？

目前项目处于课设 Agent 验证阶段，还没有做严格 TPM 压测。现阶段更关注单用户完整链路和生成质量。

如果要上线，我会从模型 TPM 限流、接口 QPS、SSE 连接数、Milvus 检索耗时、完整方案生成耗时这几个维度压测，并根据模型服务限制做排队、限流和降级。

#### 16. 你提到效率从数周缩短到分钟级，这个数据怎么来的？

这个说法是场景对比口径，不是线上统计。传统课设准备需要学生自己查资料、拆需求、设计数据库接口、写报告和准备答辩，通常需要数天到数周。

课设通生成的是初版方案和配套材料，可以把“从零开始整理”的时间缩短到分钟级。但面试中我会强调它是辅助生成初稿，不是替代完整开发和人工审核。

#### 17. 日志为什么在腾讯云上？怎么上传的？

这个问题来自 OnCall/运维类项目，不适用于课设通。课设通目前没有接腾讯云日志服务。

如果面试官追问日志，可以说课设通目前主要记录后端应用日志和工具调用日志，后续如果上线，可以接入云日志服务，用于排查调用失败、SSE 中断和 RAG 入库异常。

#### 18. 没做多租户吗？为什么？

当前没有做多租户。因为项目重点是验证 Agent、RAG、工具调用和任务编排。多租户会引入账号体系、权限、数据隔离、存储配额等复杂度。

如果后续做成学校内部平台或 SaaS，再补充多租户更合理。

#### 19. 如何处理用户上传资料的安全问题？

第一，限制文件类型和大小。第二，对文件内容做解析和清洗，避免恶意内容直接进入 prompt。第三，不把用户资料用于其他用户会话。第四，如果后续做多租户，需要按用户或项目隔离知识库数据。

#### 20. 课设通和普通 ChatGPT 有什么区别？

普通 ChatGPT 是通用问答工具。课设通是面向软件课设的垂直 Agent 系统。

区别在于课设通有课程资料 RAG、课设工具集、PAR 完整方案编排、产物生成和前端工作台。它的目标不是回答一个问题，而是帮助用户完成一套课设准备流程。

#### 21. 这个项目的业务价值是什么？

对学生来说，它降低了软件课设的入门门槛，让学生更快理解课设要做什么、怎么拆功能、怎么组织报告和答辩。

对教学场景来说，它可以作为课设辅导工具，让学生先得到结构化初稿，再把精力放在代码实现和方案优化上。

#### 22. 这个项目的技术价值是什么？

技术价值在于把 RAG、ReAct、PAR、多工具调用、SSE 和前端工作台结合起来，形成一个完整的 AI Agent 工程实践。

它展示的不是单个概念，而是如何把大模型放进一个可控业务流程里。

#### 23. 如果设计一个 Agent 去辅助增效，你还有什么想法？

可以进一步做“代码落地 Agent”。在当前课设方案、数据库和接口已经生成的基础上，让 Agent 继续生成 Spring Boot 后端代码、Vue 页面、SQL 脚本和接口文档。

这样课设通就从“方案助手”升级成“课设开发助手”，但这需要更强的代码生成、文件写入、测试和安全控制。

#### 24. 项目最后怎么总结？

可以用这段：

> 这个项目让我最大的收获是，AI 项目的重点不只是调用模型，而是如何把模型放进一个可控的业务流程里。课设通里我把 RAG、ReAct、PAR、多工具调用和 SSE 结合起来，让系统从“回答一个问题”升级为“完成一套课设任务”。后续我会继续补 RAG 评测、引用来源展示和 Agent 失败重试机制，让它更接近真实可用的 Agent 产品。
