# 课设通 Agent 助手面试准备文档

## 1. 项目定位

### 1.1 一句话介绍

课设通 Agent 助手是一个面向大学生软件课程设计场景的 AI Agent 系统，通过 RAG 知识库、ReAct 对话 Agent、PAR 多 Agent 任务编排和工具调用能力，帮助用户从课设选题、需求分析、数据库设计、接口设计、报告大纲到答辩准备形成一套可落地的完整方案。

### 1.2 面试官真正关心什么

这个项目不能只讲“我做了一个 AI 助手”，否则很容易显得泛。面试时要把项目讲成：

1. 解决了一个真实场景问题：大学生做软件课设时，不知道怎么选题、怎么拆需求、怎么设计数据库和接口、怎么写报告和准备答辩。
2. 技术上不是简单调大模型接口：系统里有 RAG、向量检索、工具调用、多轮对话记忆、SSE 流式输出、多 Agent 编排。
3. 不是只生成一段文本：最终目标是生成一整套课设产物，包括完整方案、数据库设计、接口设计、项目结构、测试用例、报告大纲和答辩问答。
4. 工程上有可运行接口和前端工作台：后端基于 Spring Boot + Spring AI Alibaba，前端提供类似 Codex 的浅色对话工作台。

## 3. 面试亮点打造

### 3.1 亮点一：不是普通聊天机器人，而是课设全流程 Agent

**普通大模型问答的问题：**

用户问“帮我做一个校园二手交易平台课设”，大模型通常会直接生成一段泛泛的方案，数据库、接口、测试、报告和答辩材料不一定完整，也很难保证符合老师的评分标准。

**课设通的做法：**

我把课设任务拆成“理解任务、规划方案、生成方案、生成配套产物、审查完整性”几个阶段，由 PAR 任务 Agent 负责总控，并联动数据库设计、接口设计、报告大纲、测试用例、答辩问答等工具。这样系统输出的不只是一个回答，而是一套可以继续落地实现和写报告的课设材料。

**面试表达：**

这个项目的核心不是“套个大模型接口”，而是把课设这个复杂任务流程化。用户输入一个题目后，系统会先由 Supervisor 判断目标和风险，再由 Planner 拆解任务，最后由 Executor 生成完整方案，同时调用产物生成工具输出数据库、接口、项目结构、测试和答辩材料。这让输出从“单段文本”变成“结构化课设交付物”。

### 3.2 亮点二：RAG 解决课设知识不可靠的问题

**没有 RAG 时：**

大模型只能依赖通用知识，可能不知道具体课程评分标准、报告模板、老师要求和已有优秀案例，生成内容容易泛化。

**有 RAG 后：**

用户可以上传课程设计任务书、评分标准、报告模板、优秀案例等资料。系统会将文档分片、向量化并写入 Milvus，Agent 在回答和生成方案时可以通过知识库工具召回相关片段，让输出更贴合课程要求。

**面试表达：**

我把 RAG 做成了一条完整链路：文件上传后先保存到本地，再由 DocumentChunkService 按 maxSize=800、overlap=100 做分片，然后调用 DashScope Embedding 生成向量，最后写入 Milvus。查询时通过 queryCourseProjectKnowledge 工具进行 TopK=3 召回，并把召回内容交给 Agent 参与回答。这样可以避免模型只凭通用知识生成答案。

### 3.3 亮点三：ReAct 对话 Agent 解决“边问边做”的交互问题

**普通对话的问题：**

如果用户问“帮我推荐选题”“这个数据库怎么设计”“这个接口怎么写”，系统如果只靠一次 prompt，很难根据问题动态选择工具。

**ReAct 的价值：**

ReAct 模式让 Agent 可以先理解用户意图，再决定是否调用知识库、选题推荐、数据库设计、接口设计等工具，最后综合工具结果生成答案。

**面试表达：**

我把自由问答场景设计成 ReAct 对话 Agent，因为课设咨询不是固定流程，用户可能随时问概念、问方案、问数据库、问接口。ReAct 更适合这种交互式问题，它能根据问题动态判断是否调用工具，而不是每次都走固定流程。

### 3.4 亮点四：PAR 任务 Agent 解决复杂课设任务拆解

**ReAct 不够的地方：**

ReAct 适合单轮或局部问题，但完整课设方案生成是一个复杂任务，包含需求、架构、数据库、接口、测试、报告、答辩等多个阶段。

**PAR 的价值：**

PAR 更适合流程化任务。Supervisor 做目标识别和风险判断，Planner 负责拆解任务和规划步骤，Executor 负责最终执行和整合。

**面试表达：**

我没有把所有任务都交给一个 Agent，而是区分了对话场景和复杂任务场景。对话场景用 ReAct，完整方案生成用 PAR。PAR 流程里 Supervisor 负责判断要做什么，Planner 负责规划怎么做，Executor 负责生成可交付结果。这样能降低复杂任务直接丢给大模型导致结构混乱的问题。

### 3.5 亮点五：工具集让 Agent 从“会说”变成“能做”

**没有工具时：**

Agent 只能生成文本，数据库设计、接口设计、报告大纲等内容全靠模型临时发挥，稳定性差。

**有工具后：**

系统将选题推荐、数据库设计、接口设计、项目结构、报告大纲、测试用例、答辩准备封装为工具，Agent 可以按需调用。

**面试表达：**

我把课设常见任务抽象成一组工具，而不是全部写在 prompt 里。这样做有两个好处：第一，工具输出更稳定，适合重复调用；第二，Agent 可以根据不同场景组合工具，比如完整方案生成时会同时调用数据库、接口、项目结构和报告工具，输出更完整。

### 3.6 亮点六：SSE 流式输出优化长文本生成体验

**没有流式输出时：**

完整课设方案生成会很长，用户可能等几十秒才看到结果，体验差，也容易误以为系统卡住。

**有 SSE 后：**

后端通过 SseEmitter 推送生成过程，前端逐步展示文本。

**面试表达：**

因为课设方案输出通常很长，我用 SSE 做流式输出。相比 WebSocket，SSE 更适合这种服务端单向推送文本的场景，实现更轻，浏览器原生支持，后端用 Spring 的 SseEmitter 就能完成。用户可以边看边等，降低长响应带来的等待感。

## 4. 成果量化建议

目前你原来的简历描述偏“做了什么”，面试里更建议改成“带来了什么结果”。下面这些量化口径可以用，但要尽量先用自己的测试数据校准。

### 4.1 可直接使用的真实工程量化

这些来自当前项目实现，比较稳：

- 覆盖 `20` 个核心测试用例，包含工具、对话、产物生成、方案审查、上传接口和 Spring 上下文测试。
- RAG 默认分片参数为 `maxSize=800`、`overlap=100`，检索 `TopK=3`。
- 支持 `7` 类课设工具产物：选题推荐、数据库设计、接口设计、项目结构、报告大纲、测试用例、答辩问答。
- 支持 `3` 类主流程：课设对话、PAR 完整方案、方案审查。
- 支持上传 `.txt`、`.md` 文档进入 RAG 知识库链路。

### 4.2 建议补测后再写的量化

这些最好后续补一个测试表再写进简历：

- 在 `20` 份课设资料样例上，RAG 召回命中率达到 `85%+`。
- 完整课设方案生成时间从人工整理的 `数小时/数天` 缩短到 `分钟级`。
- 通过工具化产物生成，将数据库设计、接口设计、报告大纲等重复材料准备时间减少 `70%+`。
- 流式输出首 token 响应时间控制在 `2s` 左右，明显改善长文本等待体验。

### 4.3 面试中更稳的说法

如果没有严格评测，不要说“准确率一定达到 85%”。可以这样说：

```text
我做过一组小规模样例验证，主要验证不同 chunk size 和 TopK 对召回效果的影响。当前默认采用 maxSize=800、overlap=100、TopK=3，是在准确率和上下文长度之间做的折中。后续如果要更严谨，会补充标准问答集，统计 Recall@K 和人工相关性评分。
```

这句话比硬说“85%+”更安全，也更像真正理解 RAG 的人。

## 5. 如何介绍项目

### 5.1 30 秒版本

我做的是一个面向大学生软件课设场景的 AI Agent 助手。它不是简单聊天机器人，而是把课设任务拆成了知识库检索、对话问答、任务规划、工具调用和产物生成几个模块。用户可以上传老师给的评分标准和报告模板，系统通过 RAG 检索相关资料，再由 ReAct 对话 Agent 或 PAR 任务 Agent 生成课设方案、数据库设计、接口设计、报告大纲和答辩准备材料。

### 5.2 1 分钟版本

这个项目解决的是大学生做软件课程设计时的真实问题。很多学生不是不会写代码，而是不知道怎么选题、怎么拆需求、怎么设计数据库接口、怎么写报告和准备答辩。所以我设计了一个课设通 Agent 助手。

系统主要有三层能力。第一层是 RAG 知识库，支持上传评分标准、报告模板、优秀案例等资料，经过分片、向量化后存入 Milvus，后续回答时可以召回相关内容。第二层是对话 Agent，基于 ReAct 模式支持自由问答、多轮上下文和即时工具调用。第三层是 PAR 任务 Agent，通过 Supervisor、Planner、Executor 拆解复杂课设任务，并联动工具生成数据库设计、接口设计、报告大纲、测试用例和答辩问答。

技术上我用了 Spring Boot、Spring AI Alibaba、DashScope、Milvus、SSE 和本地工具调用。最终前端提供了一个类似 Codex 的对话工作台，用户可以在一个页面里完成提问、上传资料、生成方案和查看产物。

### 5.3 3 分钟版本

这个项目的背景是我发现软件课设虽然看起来是写一个系统，但实际难点往往不只在编码。很多学生卡在选题、需求拆解、数据库设计、接口设计、报告结构和答辩准备上。传统做法是自己翻模板、找案例、问同学或者直接问大模型，但大模型如果没有课程资料支撑，很容易生成泛化内容，和老师评分标准不匹配。

所以我做了课设通 Agent 助手，目标是把软件课设从“零散问答”变成“可编排的任务流程”。

系统架构上，我做了三块核心能力。第一块是 RAG 知识库，用户可以上传老师给的任务书、评分标准、报告模板和优秀案例。后端会保存文件，按 maxSize=800、overlap=100 分片，然后调用 DashScope Embedding 生成向量，写入 Milvus。Agent 后续可以通过知识库工具 TopK 召回相关片段，提升回答的针对性。

第二块是 ReAct 对话 Agent，主要处理自由问答场景。比如用户问“这个题目适合什么技术栈”“数据库表怎么设计”“接口怎么拆”，Agent 会根据问题判断是否调用知识库或本地工具，再组织中文回答。这里我也做了本地会话记忆，通过 conversationId 维护多轮上下文。

第三块是 PAR 任务 Agent，主要处理完整方案生成。这个流程里有 Supervisor、Planner、Executor 三个阶段：Supervisor 判断目标、关键产物和风险；Planner 拆解功能模块、技术路线和开发顺序；Executor 生成完整课设方案。同时我把产物生成能力接进 PAR 流程，自动生成数据库设计、接口设计、项目结构、报告大纲、测试用例和答辩问答。

工程实现上，后端基于 Spring Boot 和 Spring AI Alibaba，模型用 DashScope，向量库用 Milvus，流式输出用 SSE，前端是一个类似 Codex 的浅色对话工作台。项目目前已经覆盖了上传、产物生成、方案审查、对话和任务编排等核心接口，并有 20 个测试用例保证核心流程稳定。

## 6. 面试节奏

### 6.1 推荐讲述顺序

1. 先讲背景：为什么做这个项目，真实痛点是什么。
2. 再讲整体架构：RAG 知识库、ReAct 对话 Agent、PAR 任务 Agent、工具集、前端工作台。
3. 讲三个核心亮点：RAG、ReAct/PAR 区分、工具调用与产物聚合。
4. 主动讲一个难点：比如 RAG 参数选择、复杂任务拆解、长文本流式输出。
5. 最后讲不足和改进：比如后续要补标准评测集、优化召回质量、增强多 Agent 失败恢复。

### 6.2 面试中不要这样讲

不要这样说：

```text
我做了一个 AI Agent 项目，可以帮学生生成课设。
```

这样太泛，面试官很容易觉得只是调用大模型。

建议这样说：

```text
我把软件课设这个复杂任务拆成了知识检索、自由问答、任务规划和产物生成几个阶段。对话类问题用 ReAct，完整方案类问题用 PAR，多 Agent 编排负责拆解和整合，本地工具负责稳定生成数据库、接口、报告等结构化产物，RAG 负责把老师资料和评分标准接入生成过程。
```

## 7. 常见面试题与参考回答

### 7.1 简单介绍一下这个项目

这是一个面向大学生软件课程设计场景的 AI Agent 助手。它解决的是学生在课设中常见的选题难、需求拆解难、数据库接口设计难、报告和答辩材料准备成本高的问题。系统基于 Spring Boot 和 Spring AI Alibaba 实现，核心能力包括 RAG 知识库、ReAct 对话 Agent、PAR 任务 Agent、本地工具调用和 SSE 流式输出。用户可以上传课设资料，系统通过知识库检索增强回答，也可以通过 PAR 流程生成完整课设方案和配套产物。

### 7.2 你为什么要做这个项目？

我做这个项目是因为软件课设是一个很典型的复杂任务，但很多学生并不是单点不会，而是不知道整个流程怎么走。比如选题、需求分析、数据库设计、接口设计、报告和答辩准备是互相关联的。普通大模型可以回答某个问题，但很难稳定地产出一整套符合课程要求的材料。所以我想用 Agent 编排的方式，把课设流程拆成多个阶段，让系统不仅能回答问题，还能辅助完成完整课设产物。

### 7.3 你的项目核心架构是什么？

核心架构可以分成四层。

第一层是知识库层，负责文档上传、分片、向量化、Milvus 存储和检索。第二层是工具层，封装选题推荐、数据库设计、接口设计、报告大纲、测试用例和答辩准备等能力。第三层是 Agent 层，包括 ReAct 对话 Agent 和 PAR 任务 Agent。第四层是交互层，提供前端对话工作台和 SSE 流式输出。

### 7.4 RAG 是什么？你项目里怎么用的？

RAG 是 Retrieval-Augmented Generation，也就是检索增强生成。它的核心思想是模型回答前先从外部知识库检索相关资料，再把这些资料作为上下文交给大模型生成答案。

在我的项目里，用户可以上传课设任务书、评分标准、报告模板等文档。系统会先保存文件，再进行文档分片，然后调用 DashScope Embedding 生成向量，写入 Milvus。回答问题时，Agent 可以通过知识库工具按 TopK 召回相关片段，再结合用户问题生成答案。

### 7.5 你的文档分片参数怎么选的？

我默认采用 maxSize=800、overlap=100。这个选择主要考虑两个因素：一是课设文档通常是报告模板、评分标准和案例说明，段落信息比较密集，分片太小容易丢上下文；二是分片太大又会增加召回噪声和 prompt 长度。

overlap=100 是为了避免关键信息刚好被切在两个分片边界上。TopK 采用 3，是在召回覆盖率和上下文长度之间做的折中。

如果面试官追问，我会补充：后续更严谨的做法是构建标准问答集，用 Recall@K、MRR 或人工相关性评分来评估不同 chunk size 和 TopK 的效果。

### 7.6 为什么用 Milvus？

Milvus 是专门面向向量检索的数据库，适合存储 Embedding 并做相似度搜索。我的项目里课设资料会被转成向量，后续要根据用户问题快速召回相似片段，这正是向量数据库的典型场景。

相比直接存在 MySQL 里，Milvus 对向量索引、相似度检索和大规模向量管理支持更好。即使当前数据量不大，使用 Milvus 也能让系统架构更接近真实 RAG 应用。

### 7.7 Embedding 是什么？

Embedding 是把文本转换成向量表示的过程。语义相近的文本，转换出来的向量距离也更近。比如“课程设计评分标准”和“老师如何打分”在语义上相关，向量空间里的距离也会更近。

在我的项目里，文档分片和用户查询都会通过 DashScope Embedding 转成向量，然后用 Milvus 做相似度检索。

### 7.8 ReAct 是什么？你怎么用的？

ReAct 是 Reasoning + Acting，也就是让 Agent 在推理和行动之间交替进行。它不是只生成答案，而是先判断问题需要什么信息，再决定是否调用工具，最后综合工具结果回答。

我的对话 Agent 用 ReAct 思路处理自由问答。比如用户问“帮我设计数据库”，Agent 可以调用数据库设计工具；用户问“老师评分标准里怎么要求报告”，Agent 可以调用知识库检索工具。这样对话 Agent 更像一个会用工具的小助手，而不是只会聊天。

### 7.9 PAR 或 Plan-Execute 是什么？

PAR 可以理解为 Plan-Act-Reflect 或 Plan-Execute-Replan 的任务模式。它适合处理复杂、长链路任务。核心思想是先规划，再执行，执行中如果发现信息不足或任务变化，可以重新规划。

我的项目里完整课设方案生成就用了这个思路。Supervisor 负责识别目标和风险，Planner 负责拆解任务，Executor 负责生成完整方案。后续我又把产物生成能力接进 PAR 流程，让它输出数据库设计、接口设计、报告大纲等配套材料。

### 7.10 ReAct 和 PAR 有什么区别？

ReAct 更适合交互式、局部问题，比如用户临时问一个概念、一个数据库设计建议、一个接口怎么写。它强调边想边调用工具。

PAR 更适合复杂任务，比如生成完整课设方案。它强调先规划整体步骤，再按阶段执行，最后整合结果。

所以我的项目里没有强行用一个模式解决所有问题，而是对话场景用 ReAct，完整任务场景用 PAR。

### 7.11 你的 Multi-Agent 是怎么协作的？

目前主要是 Supervisor、Planner、Executor 三阶段协作。Supervisor 先分析用户课设目标、关键产物和风险点；Planner 根据 Supervisor 的结果拆解功能模块、技术路线、数据库接口和开发顺序；Executor 根据前两者的结果生成完整方案。然后系统会联动 ArtifactGenerationService 生成数据库设计、接口设计、项目结构、报告大纲、测试用例和答辩问答。

从工程上看，这是顺序编排式协作，优点是流程稳定、可解释，适合课设这种结构化任务。

### 7.12 Agent 是怎么实现工具调用的？

我把课设相关能力封装成 Spring Bean 工具类，例如 TopicRecommendTools、DatabaseDesignTools、ApiDesignTools、ProjectTemplateTools、ReportTools、DefenseTools 和 CourseKnowledgeTools。然后通过 CourseAgentToolRegistry 统一注册，传给 Spring AI 的 ChatClient 请求。

当 Agent 判断需要工具时，可以调用这些工具，把工具输出作为生成答案的依据。

### 7.13 Function Calling 的流程是什么？

Function Calling 的流程可以概括为：先把工具名称、参数结构和工具描述暴露给模型；模型根据用户问题判断是否需要调用工具；如果需要，模型生成工具调用参数；服务端执行具体函数；最后把工具结果返回给模型，由模型组织最终回答。

在我的项目里，工具描述都用中文编写，方便模型在中文课设场景下正确理解工具用途。

### 7.14 你有哪些工具？

主要有七类工具：

1. 选题推荐工具：根据方向推荐适合课设的题目。
2. 数据库设计工具：生成核心表、字段和关系设计。
3. 接口设计工具：生成 REST API 路径、请求参数和响应结构。
4. 项目结构工具：给出前后端项目目录建议。
5. 报告工具：生成课程设计报告大纲。
6. 答辩工具：生成常见答辩问题和回答思路。
7. 知识库工具：调用 RAG 检索课设资料。

### 7.15 为什么要做会话记忆？

课设咨询通常不是一次性问答。用户可能先问选题，再追问数据库，再继续问报告怎么写。如果没有上下文记忆，每次都要重新说明题目和技术栈，体验很差。

所以我做了基于 conversationId 的本地会话记忆，保存最近多轮对话，让 Agent 能结合前面的上下文继续回答。

### 7.16 SSE 是什么？为什么不用 WebSocket？

SSE 是 Server-Sent Events，适合服务端向浏览器持续推送文本。课设方案生成是典型的服务端单向输出场景，用户提交请求后，服务端不断推送生成内容即可。

WebSocket 更适合双向实时通信，比如聊天房间、协同编辑。我的场景不需要复杂双向通信，所以 SSE 更轻量，Spring 里也可以直接用 SseEmitter 实现。

### 7.17 你的 Prompt 怎么设计的？

我没有只写一个大 prompt，而是按 Agent 职责拆开。

对话 Agent 的 prompt 强调中文回答、课设场景、可调用工具、必要时结合知识库。PAR 任务 Agent 则拆成 Supervisor、Planner、Executor 三个 prompt：Supervisor 负责目标和风险，Planner 负责规划，Executor 负责最终方案。这样可以降低一个 prompt 同时承担所有职责导致输出混乱的问题。

### 7.18 如何避免大模型幻觉？

我主要从三方面降低幻觉。

第一是 RAG，让模型回答前先检索老师资料、评分标准和模板。第二是工具调用，把数据库设计、接口设计、报告大纲等相对固定的内容交给工具生成，减少模型自由发挥。第三是 prompt 约束，要求模型明确假设，对不确定内容不能伪造来源。

当然，幻觉不能完全消除，后续可以加入引用来源展示、结果审查 Agent 和人工确认机制。

### 7.19 如果工具调用错了怎么办？

当前实现中，单个产物生成失败不会让整个 PAR 流程完全崩掉，而是记录到 failedArtifacts 中，并返回“该产物生成失败”的中文提示。这样用户至少能拿到主方案和其他产物。

后续可以继续优化为自动重试、降级到模板生成、或者让 Planner 重新规划缺失产物。

### 7.20 你的项目最大难点是什么？

我认为最大难点不是调用大模型，而是把一个复杂的课设任务拆成稳定、可解释、可组合的流程。因为课设不是一个单点问题，它涉及知识检索、任务规划、产物生成和结果审查。为了解决这个问题，我把系统拆成 RAG、ReAct、PAR 和工具集几层，让不同模块各自解决合适的问题。

### 7.21 你觉得项目最有价值的地方是什么？

最有价值的地方是它把课设准备从“零散问答”变成了“结构化流程”。用户不只是拿到一段回答，而是可以得到完整方案、数据库设计、接口设计、报告大纲、测试用例和答辩问答。这个结果更接近真实课设交付物。

### 7.22 项目有什么不足？

目前主要有三个不足。

第一，RAG 评测还不够体系化，需要构建标准问答集来评估召回效果。第二，多 Agent 编排目前以顺序流程为主，后续可以增加更细的反思和重试机制。第三，知识库管理还比较轻量，后续可以支持更多格式，比如 PDF、DOCX，并展示更完整的引用来源。

### 7.23 如果重新设计，你会怎么改？

我会重点改三点。第一，引入更系统的 RAG 评测，包括 Recall@K、人工相关性评分和答案质量评分。第二，把 PAR 流程做得更像真正的工作流引擎，每个子产物都有状态、重试和降级策略。第三，增强前端的知识引用展示，让用户能看到答案来自哪些文档片段。

### 7.24 你的项目部署方式是什么？

当前是 Spring Boot 单体应用，前端静态资源直接放在 `src/main/resources/static`，后端提供 REST 和 SSE 接口。运行时需要配置 DashScope API Key，并启动 Milvus。应用默认端口是 9900。

后续如果部署到服务器，可以把 Spring Boot 打成 jar，Milvus 单独用 Docker 部署，DashScope Key 通过环境变量注入。

### 7.25 为什么不用 LangChain？

这个项目后端主体是 Java 和 Spring Boot，而 Spring AI Alibaba 和 Spring 生态结合更自然。它能直接复用 Spring 的 Bean 管理、配置、测试、Controller 和服务层结构，工具调用也可以和现有 Spring Bean 结合。

LangChain 更常见于 Python 生态，能力很强，但在这个项目里会增加跨语言集成成本。所以我选择 Spring AI Alibaba，是为了更贴近 Java 工程项目的落地方式。

### 7.26 为什么使用 Spring AI Alibaba？

因为项目使用的是 Java 技术栈，并且模型服务用的是 DashScope。Spring AI Alibaba 对阿里云通义模型和 DashScope 生态支持更直接，同时能和 Spring Boot 的配置、依赖注入、测试体系结合。这样工程集成成本低，也更适合放在 Java 后端项目里展示。

### 7.27 MCP 在项目里怎么理解？

MCP 可以理解为一种让 Agent 标准化连接外部工具和上下文的协议。它的价值是把工具能力从模型本身解耦出来，让 Agent 可以通过统一协议访问外部系统、文件、服务或工具。

在这个项目里，MCP 可以作为扩展工具接入方向，比如后续接入代码生成器、文档解析器、在线资料检索工具等。简历里提到 MCP 时，要强调它是扩展能力，不要讲成所有能力都依赖 MCP。

### 7.28 你怎么评价 Prompt 好坏？

我主要看四点：输出是否稳定、结构是否符合预期、是否能正确调用工具、是否能处理异常输入。

比如 PAR 的 prompt，我会看它是否固定输出任务目标、关键产物、执行阶段和风险点；对话 prompt 则看它是否能保持中文课设场景，不跑题，不编造不存在的资料。

### 7.29 你怎么做意图识别？

当前主要通过模式入口和 prompt 约束做显式意图识别。用户选择“课设对话”“PAR 完整方案”“方案审查”后，后端进入不同处理流程。

后续可以增加自动意图分类，比如根据用户输入判断是选题推荐、知识库问答、完整方案生成还是方案审查，再自动路由到不同 Agent。

### 7.30 为什么没有做多租户？

这个项目当前定位是课设 Agent 助手和技术验证，重点是 RAG、Agent 编排和工具调用。多租户属于平台化能力，会引入用户、权限、数据隔离等复杂度。当前阶段先把核心 Agent 能力跑通更重要，后续如果做成 SaaS 或学校内部平台，再补多租户更合理。

## 11. 高频面试题全量速答

本节覆盖你图片里的 63 个问题，并额外按课设通项目做了适配。注意：图片里有些问题来自 OnCall/运维类项目，例如 Eino、运维 Agent、腾讯云日志等。课设通项目最终技术栈是 Spring Boot + Spring AI Alibaba，不要硬套不属于本项目的内容。遇到这类问题时，要主动说明“我这个项目里对应的是课设任务 Agent / Spring AI Alibaba / 课设知识库”。

### 11.1 简单介绍一下这个项目

课设通 Agent 助手是一个面向大学生软件课程设计场景的 AI Agent 系统。它解决的是学生在课设中常见的选题难、需求拆解难、数据库接口设计难、报告和答辩材料准备成本高的问题。系统基于 Spring Boot 和 Spring AI Alibaba 实现，结合 RAG 知识库、ReAct 对话 Agent、PAR 任务 Agent、本地工具调用和 SSE 流式输出，支持从资料上传、知识检索、方案生成到配套产物生成的一站式流程。

### 11.2 简单说说 Eino 是什么框架

Eino 是字节跳动开源的 Go 语言 AI 应用开发框架，主要用于构建大模型应用、Agent、RAG、工具调用和工作流编排。它和 LangChain 类似，都是帮助开发者把模型、工具、知识库和流程组织起来的框架。

但要注意：课设通项目没有使用 Eino，课设通使用的是 Java 生态下的 Spring AI Alibaba。面试里如果被问到 Eino，可以说了解它的定位，但本项目为了贴合 Java/Spring 技术栈，选择了 Spring AI Alibaba。

### 11.3 简单说说 Spring AI Alibaba 是什么框架

Spring AI Alibaba 是 Spring AI 在阿里云通义千问、DashScope 等模型生态上的扩展能力。它能把大模型调用、ChatClient、Embedding、工具调用等能力接入 Spring Boot 项目，并利用 Spring 的依赖注入、配置管理、测试体系和 Web 框架能力。

课设通选择它，是因为项目本身是 Java 后端项目，Spring AI Alibaba 能和 Spring Boot 融合得更自然，也更方便把工具类注册成 Spring Bean 给 Agent 调用。

### 11.4 为什么选择 Eino，不用 LangChain

这个问题不完全适用于课设通，因为课设通没有选择 Eino。如果面试官按参考项目问，可以这样转回来：

```text
我这个项目最终没有选 Eino，也没有选 LangChain，而是选了 Spring AI Alibaba。原因是项目主技术栈是 Java + Spring Boot，Spring AI Alibaba 能直接复用 Spring 的 Bean 管理、配置、Controller 和测试体系；而 LangChain 更偏 Python 生态，Eino 更偏 Go 生态。对这个项目来说，Spring AI Alibaba 的工程集成成本更低。
```

### 11.5 为什么选择 Spring AI Alibaba，不用 LangChain

因为课设通是 Java/Spring Boot 项目。Spring AI Alibaba 能直接对接 DashScope，并且能把工具类、服务类、配置类都纳入 Spring 容器，和现有后端工程融合更好。

LangChain 很适合 Python AI 应用，但如果在 Java 项目里强行引入，会增加跨语言部署和调用成本。这个项目更看重工程落地和 Java 技术栈一致性，所以选择 Spring AI Alibaba 更合适。

### 11.6 简单介绍一下你设计的几个 Agent

主要有两个主 Agent。

第一个是 ReAct 课设对话 Agent，用于自由问答、概念解释、局部方案讨论和即时工具调用。比如用户问选题、数据库、接口、报告怎么写，都可以走对话 Agent。

第二个是 PAR 课设任务 Agent，用于完整课设方案生成。它内部拆成 Supervisor、Planner、Executor 三个阶段，分别负责目标识别、任务拆解和最终方案生成。后续又把产物生成能力接进 PAR 流程，自动输出数据库设计、接口设计、项目结构、报告大纲、测试用例和答辩问答。

### 11.7 知识库的使用场景是什么

知识库主要用于解决大模型缺少课程上下文的问题。用户可以上传老师给的任务书、评分标准、报告模板、优秀案例等资料。系统把这些资料分片、向量化、写入 Milvus，后续用户问问题或生成方案时，Agent 可以检索这些资料作为上下文。

典型场景包括：根据评分标准生成报告结构、根据任务书提取功能要求、根据模板生成报告大纲、根据优秀案例借鉴模块设计。

### 11.8 对话 Agent 的使用场景是什么

对话 Agent 适合自由问答和局部问题。例如：

- 帮我推荐几个适合 Java Web 的课设题目
- 校园二手交易平台应该有哪些模块
- 这个系统数据库表怎么设计
- 接口怎么拆
- 报告摘要怎么写

这些问题不一定需要完整规划流程，所以用 ReAct 对话 Agent 更合适。它可以根据问题动态调用知识库或工具。

### 11.9 你刚才提到 RAG，详细说下 RAG 吧

RAG 是检索增强生成。它不是让模型凭空回答，而是在回答前先从外部知识库检索相关资料，再把资料作为上下文交给模型。

课设通里的 RAG 流程是：用户上传课设资料，后端保存文件，然后由 DocumentChunkService 分片，再调用 DashScope Embedding 生成向量，写入 Milvus。查询时，系统把用户问题也转成向量，在 Milvus 里做相似度检索，召回 TopK 相关文档片段，再交给 Agent 生成答案。

### 11.10 你刚才提到 ReAct，详细说下 ReAct 吧

ReAct 是 Reasoning + Acting。它让 Agent 不只是直接回答，而是边推理边决定是否采取行动，比如调用工具或检索知识库。

在课设通里，对话 Agent 使用 ReAct 思路。用户问“帮我设计数据库”，Agent 会判断这个问题适合调用数据库设计工具；用户问“老师评分标准怎么要求报告”，Agent 会调用知识库检索工具。工具结果再被整合成最终回答。

### 11.11 课设任务 Agent 的使用场景是什么

课设任务 Agent 对应图片里的“运维 Agent”，但在课设通里它处理的是完整课设任务，而不是运维排障。

它适合复杂、流程化任务，比如用户输入“我要做校园二手交易平台，请给我完整课设方案”。这类任务不能只回答一段话，需要先理解目标，再拆解模块，再生成数据库、接口、项目结构、测试、报告和答辩材料，所以更适合 PAR 流程。

### 11.12 Plan-Execute-Replan 是什么意思

Plan-Execute-Replan 是一种复杂任务处理模式。Plan 是先规划任务步骤，Execute 是按步骤执行，Replan 是执行中遇到异常、信息不足或结果不符合预期时重新规划。

课设通目前实现的是 Supervisor + Planner + Executor 的顺序式 PAR 雏形。后续如果加强 Replan，可以在某个产物生成失败时让 Planner 重新调整任务，或者降级到模板产物生成。

### 11.13 ReAct 和 Plan-Execute-Replan 有什么区别

ReAct 更适合交互式、局部问题，强调边思考边调用工具。比如用户问一个接口怎么设计，Agent 可以直接调用接口设计工具。

Plan-Execute-Replan 更适合复杂长任务，强调先规划，再执行，必要时重新规划。比如完整课设方案生成需要多个阶段和多个产物，就更适合 PAR。

课设通里，对话场景用 ReAct，完整方案场景用 PAR。

### 11.14 你提到响应时间从小时级降到分钟级，数据怎么来的

这个量化口径要谨慎。可以说这是基于典型课设准备流程的估算，而不是大规模线上统计。

人工准备一个完整课设方案，通常需要查模板、拆需求、设计数据库接口、写报告大纲和准备答辩问题，至少是小时级甚至天级。系统自动生成这些结构化产物，单次请求可以在分钟级得到初稿。

如果要写进简历，建议写“将课设材料初稿准备从小时级缩短到分钟级”，不要写成严格生产指标。后续可以通过固定样例任务做计时测试来补强。

### 11.15 文档分块大小和检索 TopK 参数怎么选择

当前默认分片参数是 maxSize=800、overlap=100，TopK=3。

maxSize=800 是因为课设文档通常段落较完整，太小容易切碎上下文，太大又会带入噪声。overlap=100 是为了避免关键信息被切在边界处。TopK=3 是为了在召回覆盖率和 prompt 长度之间做平衡。

后续如果要更严谨，会构建标准问答集，用 Recall@K、MRR 和人工相关性评分比较不同参数。

### 11.16 多轮对话和上下文记忆是什么意思

多轮对话是指用户连续提问时，系统能记住前面的主题和约束。比如用户先说“我要做校园二手交易平台”，后面再问“数据库怎么设计”，系统应该知道还是这个题目。

课设通通过 conversationId 管理本地会话记忆，保存最近多轮消息，让 Agent 在后续回答时能结合上下文。

### 11.17 通过 SSE 实现流式输出，为什么不用 WebSocket

课设通的流式输出是服务端向客户端持续推送生成文本，属于单向推送场景。SSE 正好适合这种场景，浏览器原生支持，后端用 Spring 的 SseEmitter 就能实现。

WebSocket 更适合双向实时通信，比如聊天房间或协同编辑。课设方案生成不需要复杂双向通信，所以 SSE 更轻、更简单。

### 11.18 详细说一下 SSE 核心怎么实现

后端 Controller 返回 SseEmitter，先发送 request 事件告诉前端请求 ID，然后订阅模型流式输出。每收到一个文本 chunk，就通过 emitter.send 发送 message 事件。完成时发送 done 事件，异常时发送 error 事件。

前端通过 fetch 读取 ReadableStream，按 SSE 的 event/data 格式解析，然后把内容逐步追加到对话消息里。

### 11.19 简历上写了 MCP 工具，谈谈你对 MCP 的理解

MCP 是 Model Context Protocol，可以理解为让 Agent 标准化连接外部工具、上下文和服务的一种协议。它的价值是把工具能力和模型解耦，让不同工具可以通过统一协议被 Agent 调用。

课设通目前核心工具主要是本地 Spring Bean 工具，MCP 更适合作为后续扩展方向，比如接入文档解析器、代码生成器、在线资料检索工具等。面试时不要夸大成“所有能力都基于 MCP”，更稳的说法是“保留了 MCP 扩展思路”。

### 11.20 你的工具集有哪些 Tool，分别有什么功能

主要工具包括：

1. TopicRecommendTools：根据方向推荐课设题目。
2. DatabaseDesignTools：生成数据库表、字段和关系建议。
3. ApiDesignTools：生成 REST API 路径、请求参数和响应结构。
4. ProjectTemplateTools：生成项目目录结构。
5. ReportTools：生成课程设计报告大纲。
6. DefenseTools：生成答辩问题和回答思路。
7. CourseKnowledgeTools：调用 RAG 知识库检索课设资料。

这些工具让 Agent 不只是聊天，而是能调用稳定能力完成具体任务。

### 11.21 向量数据库为什么使用 Milvus

Milvus 是专门做向量存储和相似度检索的数据库，适合 RAG 场景。课设资料被 Embedding 成向量后，需要根据用户问题快速召回相似内容，这就是 Milvus 的典型使用场景。

相比把向量存在普通关系型数据库里，Milvus 在向量索引、相似度检索、向量字段管理方面更专业，也更接近真实 AI 应用架构。

### 11.22 你的项目怎么部署

当前是 Spring Boot 单体应用，前端静态资源放在 `src/main/resources/static`，后端提供 REST 和 SSE 接口。运行时需要配置 DashScope API Key，并启动 Milvus。默认端口是 9900。

如果正式部署，可以把 Spring Boot 打成 jar，Milvus 用 Docker 部署，DashScope API Key 通过环境变量注入，前端由 Spring Boot 直接托管。

### 11.23 你的项目用的是什么模型

项目通过 Spring AI Alibaba 对接 DashScope，主要使用通义千问系列 chat model 做对话和方案生成，Embedding 使用 DashScope 的 text-embedding-v4。

面试时可以补充：具体模型可以通过配置切换，系统设计上不和某一个模型强绑定。

### 11.24 为什么用这个模型

因为项目使用 Spring AI Alibaba，DashScope 在 Java/Spring 生态下接入比较顺畅，同时支持 Chat 和 Embedding，能同时满足对话生成和 RAG 向量化需求。

另外，课设通主要面向中文课设场景，通义千问系列对中文理解和生成比较友好。

### 11.25 项目遇到什么困难或挑战

主要挑战有三个。

第一是如何避免项目变成普通大模型问答，所以我引入了 RAG、工具调用和 PAR 编排。第二是 RAG 参数选择，需要在分片大小、召回数量和上下文长度之间平衡。第三是复杂任务输出容易混乱，所以我把完整课设生成拆成 Supervisor、Planner、Executor，并把产物生成工具接入主流程。

### 11.26 召回与重排的区别是什么

召回是从大量文档片段里快速找出一批可能相关的候选内容，比如 TopK=10。重排是在候选内容里进一步精排，选出最相关的几个片段，比如最终取 TopK=3。

课设通目前主要实现向量召回，还没有引入专门的 rerank 模型。后续可以增加重排阶段，提高复杂问题下的检索精度。

### 11.27 Agent 是什么意思

Agent 可以理解为具备一定自主决策能力的大模型应用。它不只是回答问题，还能理解目标、拆解任务、调用工具、使用知识库，并根据结果生成最终答案。

在课设通里，Agent 的价值是把用户“帮我做一个课设”这种复杂目标拆成可执行步骤，并调用工具生成具体产物。

### 11.28 Agent 是怎么实现工具调用的

工具调用的实现方式是把本地工具类注册成 Spring Bean，并通过 CourseAgentToolRegistry 统一收集，再传给 Spring AI ChatClient。工具方法通过注解和描述暴露给模型，模型根据问题判断是否调用对应工具。

执行流程是：模型判断需要工具 -> 生成工具参数 -> 后端执行工具方法 -> 工具结果返回给模型 -> 模型整合成最终回答。

### 11.29 Function Calling 的实现流程是什么

Function Calling 的流程包括四步。

第一，把工具名称、描述和参数结构告诉模型。第二，模型根据用户问题判断是否调用工具。第三，服务端执行工具函数并得到结果。第四，把工具结果交回模型，让模型生成最终回答。

课设通里，数据库设计、接口设计、知识库检索等都可以作为 Function Calling 的工具能力。

### 11.30 Embedding 是什么意思

Embedding 是把文本转换成向量的过程。语义相近的文本，向量距离也会更近。

比如“报告评分标准”和“老师怎么给课程设计打分”语义相近，它们在向量空间中的距离就可能更近。课设通用 Embedding 把文档分片和用户查询都变成向量，再通过 Milvus 做相似度检索。

### 11.31 召回的相似度算法是什么

当前 Milvus 配置里使用 L2 距离做向量相似度检索。L2 距离越小，说明两个向量越接近，文本语义越相似。

也可以使用 cosine 相似度或 inner product，具体选择要和 Embedding 模型、向量归一化方式以及 Milvus 索引配置匹配。

### 11.32 对话 Agent Prompt 怎么写的

对话 Agent 的 prompt 核心约束是：全程中文、围绕软件课程设计场景、优先给可执行建议、必要时调用知识库和课设工具、对不确定信息不要编造。

它更关注“交互式帮助”，比如解释概念、推荐选题、补充数据库或接口设计。

### 11.33 课设任务 Agent Prompt 怎么写的

图片里问“运维 Agent”，对应到课设通就是课设任务 Agent。

课设任务 Agent 的 prompt 被拆成 Supervisor、Planner、Executor。Supervisor 负责判断目标、关键产物和风险；Planner 负责功能模块、技术栈、数据库接口和开发排期规划；Executor 负责生成最终完整课设方案。

这种拆分能让每个阶段职责更清楚，避免一个 prompt 同时承担所有任务导致输出松散。

### 11.34 如果 Agent 召回答案不准确，大模型会胡说八道吗

有可能，所以需要约束。

我的处理思路是：第一，prompt 中要求模型不要伪造来源；第二，工具结果只作为上下文，不让模型无约束扩写；第三，后续可以增加引用来源展示和答案审查机制。如果知识库没有召回到可靠内容，模型应该说明“知识库中没有找到明确依据”，再给出通用建议。

### 11.35 你知道 Agentic RAG 吗

Agentic RAG 是把 RAG 从固定检索流程升级成由 Agent 主动决策的检索流程。普通 RAG 往往是“用户问题 -> 检索 -> 生成”，而 Agentic RAG 可以让 Agent 判断是否需要检索、检索什么关键词、是否需要多次检索、是否需要结合工具。

课设通的知识库工具已经具备 Agentic RAG 的雏形，因为对话 Agent 可以按需调用知识库工具，而不是每次都固定检索。

### 11.36 混合 RAG 有什么好处

混合 RAG 通常指结合向量检索、关键词检索、结构化过滤、重排等多种方式。好处是能弥补单一向量检索的不足。

比如课程评分标准里有明确关键词“数据库设计 20 分”，关键词检索可能比纯向量更稳定；而语义问题“老师更看重哪些设计”则适合向量检索。后续课设通可以结合 BM25 + 向量检索 + rerank。

### 11.37 项目背景是什么，为什么会有这个项目

背景是软件课程设计对学生来说不是单纯写代码，而是完整工程材料准备。很多学生卡在选题、需求分析、数据库设计、接口设计、报告和答辩上。

普通大模型能回答问题，但没有课程资料支撑，容易泛化；手工翻模板又很耗时。所以我做课设通，把 RAG、Agent 和工具调用结合起来，让课设从零散问答变成结构化流程。

### 11.38 这个项目是用来做什么的

它用来辅助大学生完成软件课程设计。用户可以上传课程资料，咨询课设问题，生成完整方案，生成数据库设计、接口设计、报告大纲、测试用例和答辩问答，也可以审查已有方案的完整性。

### 11.39 你在项目里是什么角色

我是项目负责人，主要负责需求分析、系统架构设计、后端 Agent/RAG/工具模块实现、前端工作台设计、接口联调和测试验证。

可以强调：这个项目不是只做页面或接口，而是从产品定位、Agent 架构、RAG 链路、工具抽象到前后端联调都参与了。

### 11.40 项目的核心指标是什么

可以从三类指标讲。

第一是效果指标：RAG 召回相关性、方案完整性、产物覆盖度。第二是体验指标：首 token 时间、完整方案生成耗时、流式输出稳定性。第三是工程指标：接口成功率、测试覆盖、异常降级能力。

当前已经有 20 个核心测试用例，后续会补标准问答集来评估 RAG 召回和答案质量。

### 11.41 项目难点是什么，最大的困难是什么

最大的困难是如何让系统稳定完成一个复杂课设任务，而不是只生成一段看似合理的文本。

解决方式是把任务拆成 RAG、ReAct、PAR 和工具集。RAG 解决知识来源，ReAct 解决自由问答，PAR 解决复杂任务拆解，工具集解决结构化产物稳定生成。

### 11.42 你觉得做得最好的点是什么

我觉得最好的点是架构拆分比较清楚，没有把所有能力都塞进一个 prompt。系统根据场景区分 ReAct 对话 Agent 和 PAR 任务 Agent，并通过工具集输出结构化产物。

这个设计让项目从“问答 demo”更接近一个真实 Agent 应用。

### 11.43 项目有哪些不足，如何改进

不足主要有三点。

第一，RAG 评测还不够系统，需要标准问答集。第二，多 Agent 编排目前偏顺序流程，后续可以增加 Replan、重试和降级机制。第三，知识库管理还比较轻量，后续可以支持 PDF、DOCX、引用来源展示和文档删除重建索引。

### 11.44 你知道 Agent Skills 吗

Agent Skills 可以理解为给 Agent 配置的一组可复用能力包，里面可能包含工具、提示词、知识、流程或操作规范。它的作用是让 Agent 在特定领域更稳定地完成任务。

课设通里的工具集和 Prompt 体系可以看成一种领域 Skill 雏形，比如“数据库设计 Skill”“报告生成 Skill”“答辩准备 Skill”。

### 11.45 对话 Agent 如何处理超出上下文窗口的长对话

目前项目使用本地会话记忆保存最近多轮对话，适合短中期上下文。对于超长对话，后续可以采用摘要记忆策略：把早期对话压缩成摘要，只保留最近几轮原文，同时把重要事实写入长期记忆。

这样既能控制 token 长度，也能保留关键信息。

### 11.46 RAG 如何处理文档更新，增量索引怎么做

当前上传同名文件时，会先删除该文件对应的旧向量，再重新分片和入库。这样可以避免旧版本内容污染检索结果。

更完整的增量索引方案是记录文档 hash。如果文件内容没变就跳过索引；如果变了，只重新处理变化文档。大规模场景还可以按文档 ID 和 chunk ID 做局部更新。

### 11.47 Multi-Agent 具体怎么实现协作

当前采用顺序编排式协作。Supervisor 先输出任务目标和风险，Planner 基于 Supervisor 结果拆解功能模块、技术路线和开发步骤，Executor 基于前两个阶段生成完整方案。随后系统调用 ArtifactGenerationService 生成配套产物并聚合返回。

这种方式虽然没有复杂并发调度，但可解释、稳定，适合课设这种结构化流程。

### 11.48 如何保证大模型不会调用错误工具或传递错误参数

主要靠三点。

第一，工具描述写清楚，参数含义明确。第二，后端工具方法做参数校验，比如课设题目不能为空、不支持的产物类型直接返回中文错误。第三，对工具结果进行结构化封装，失败时返回 failedArtifacts，不让整个流程静默失败。

### 11.49 如何避免大模型产生幻觉

不能完全避免，但可以降低。

课设通通过 RAG 提供外部依据，通过工具调用生成稳定产物，通过 prompt 要求模型明确假设、不编造来源。后续还可以增加引用来源展示、答案审查 Agent 和人工确认步骤。

### 11.50 如果重新设计系统，你会做哪些改进

我会做四点改进。

第一，做标准 RAG 评测集。第二，引入混合检索和 rerank。第三，把 PAR 流程做成更完整的状态机，每个子产物都有状态、重试和降级。第四，增强前端引用展示，让用户知道答案依据来自哪些文档。

### 11.51 怎么解决幻觉

回答时可以更聚焦：

```text
我会从输入、过程、输出三层处理。输入层用 RAG 提供可靠资料；过程层用工具调用减少模型自由发挥；输出层用审查和引用来源让用户能校验答案。幻觉不能完全消除，但可以通过这些机制降低风险。
```

### 11.52 怎么评价 Prompt 写得好坏，如何评测

Prompt 评估可以看四类指标：格式稳定性、任务完成度、工具调用准确率、异常输入处理能力。

课设通可以准备一组固定问题，比如选题推荐、数据库设计、完整方案、方案审查，然后看输出结构是否稳定、是否调用了正确工具、是否符合中文课设场景。

### 11.53 怎么实现用户意图识别

当前采用显式模式选择：课设对话、PAR 完整方案、方案审查。用户选择不同模式后进入不同服务流程。

后续可以做自动意图识别，用一个轻量分类 prompt 或规则模型判断用户是想问答、生成完整方案、上传资料、生成单项产物还是审查方案，再自动路由。

### 11.54 没做多租户吗，为什么

当前没有做多租户。因为项目重点是验证 Agent、RAG、工具调用和任务编排，做多租户会引入账号、权限、数据隔离、计费等复杂度。

如果后续做成学校内部平台或 SaaS，再补多租户会更合理。

### 11.55 如果设计一个 Agent 去辅助增效，你有什么想法

可以把课设通进一步设计成“课设执行助手”。除了生成方案，还能根据用户选择的技术栈生成代码骨架、数据库 SQL、接口文档、测试计划和答辩 PPT 大纲。

它可以跟踪用户当前进度，比如需求已完成、数据库未完成、报告缺测试截图，然后主动提示下一步该补什么。

### 11.56 压力面：你们项目的 TPM 是多少

这个问题如果没有真实压测，不要瞎编。可以回答：

```text
目前项目处于课程设计 Agent 验证阶段，还没有做严格 TPM 压测。现阶段更关注单用户完整链路和生成质量。后续如果要上线，会从模型 TPM 限流、接口 QPS、SSE 连接数、Milvus 检索耗时几个维度做压测。
```

### 11.57 压力面：这个项目看起来很简单，有没有深入技术点

可以这样回答：

```text
如果只看表面，它像是一个 AI 问答系统。但深入点在于我没有只调模型接口，而是把课设任务拆成 RAG 知识库、ReAct 对话、PAR 编排、工具调用、SSE 流式输出和结构化产物聚合。真正难的是让模型稳定完成一个完整业务流程，而不是只生成一段文本。
```

### 11.58 Agent 执行异常或失败怎么处理

当前主要做了三类处理。

第一，参数校验，比如课设题目、产物类型不能为空。第二，工具执行失败时返回中文错误。第三，PAR 聚合中某个产物失败时记录到 failedArtifacts，不让整个主流程完全不可用。

后续可以增加自动重试、降级模板和 Replan。

### 11.59 有了 Skill 之后项目哪里可以改进

可以把当前工具集进一步抽象成 Skill。比如数据库设计 Skill 包含表结构模板、常见实体、字段规范；报告 Skill 包含报告章节、评分标准、写作模板；答辩 Skill 包含常见问题和回答套路。

这样 Agent 不只是临时调用工具，而是具备更稳定的领域能力包。

### 11.60 日志为什么在腾讯云上，怎么上传的

这个问题来自 OnCall 项目，不适用于当前课设通项目。课设通目前没有接腾讯云日志服务。

如果面试官问部署和日志，可以如实说：当前是本地 Spring Boot 应用，日志使用 Spring Boot 默认日志体系输出到控制台；后续如果部署到云上，可以接入云日志服务或 ELK，把接口调用、Agent 执行阶段、工具调用结果和异常栈统一采集。

### 11.61 项目测评怎么做的

目前主要做了工程测试和小规模功能验证。工程测试包括工具 smoke test、Controller 测试、上传接口测试、会话记忆测试、文档分片测试和 Spring 上下文测试，目前有 20 个核心测试用例。

后续效果测评会补充 RAG 标准问答集、方案完整性人工评分、工具调用准确率和生成耗时统计。

### 11.62 调用日志服务如何保证上下文不爆

如果是课设通项目，可以转成“长上下文控制”来回答。

对话上下文不应该无限塞入 prompt。可以保留最近 N 轮原文，把更早的对话压缩成摘要；RAG 检索只放 TopK 高相关片段；工具返回也要做摘要或结构化裁剪。这样能控制 token 使用，避免上下文过长。

### 11.63 Prompt 中 system prompt、历史摘要、最近几轮对话的顺序怎么排，顺序有什么影响

推荐顺序是：system prompt 最前面，其次是长期记忆或历史摘要，再放最近几轮对话，最后放当前用户问题和检索/工具结果。

原因是 system prompt 用来规定角色、边界和输出格式，优先级最高；历史摘要提供长期背景；最近几轮对话保留即时上下文；当前问题和工具结果最贴近本轮回答。

顺序会影响模型注意力。如果把当前问题放太前、约束放太后，模型可能忽略系统规则；如果历史内容太多，又会稀释当前问题。所以要控制长度并保持结构清晰。

## 12. 额外补充高频追问

### 12.1 课设通和普通 ChatGPT 有什么区别

普通 ChatGPT 主要是通用问答，课设通是面向软件课设场景做了领域化增强。它有课设资料知识库、课设工具集、PAR 任务编排和结构化产物输出。用户最终得到的是完整方案和配套产物，而不是一段泛泛回答。

### 12.2 你的 RAG 为什么不直接把所有文档塞进 prompt

因为文档多了以后会超过上下文窗口，而且无关内容会干扰模型。RAG 的价值是先检索相关片段，只把最相关内容放进 prompt，既节省 token，也减少噪声。

### 12.3 为什么要把产物生成接入 PAR，而不是单独做按钮

因为用户要的是完整课设结果，不是一个个孤立产物。PAR 主流程知道整体需求和规划，接入产物生成后，数据库、接口、报告、测试这些内容能共享同一个上下文，结果更一致。

### 12.4 你的系统如何降级

如果大模型不可用，规则型工具仍可生成部分产物，比如报告大纲、测试用例和完整性审查。RAG 入库失败时，文件保存结果会返回给前端，并明确提示向量入库失败原因。PAR 子产物失败时记录 failedArtifacts，主方案不一定整体失败。

### 12.5 你会如何继续优化这个项目

短期优化是补齐 DashScope 和 Milvus 联调，完善 RAG 引用展示。中期优化是增加混合检索、rerank 和 RAG 评测集。长期优化是把 PAR 流程做成可观测的工作流，每个子 Agent 有状态、重试、降级和质量评估。
